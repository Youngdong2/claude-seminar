## 핵심 요점 (Key Points)

1. **하네스 엔지니어링으로 AI 모델 독립적 멱등성 확보**: 클로드, 제미나이, 코덱스 등 어떤 AI 모델을 사용하더라도 하네스 엔지니어링 기법을 활용하면 일관되고 강건한 소프트웨어 결과물을 얻을 수 있다.
2. **CPS 프레임워크로 요구사항 구조화**: 고객의 비정형적인 요구사항을 Context(맥락)-Problem(문제)-Solution(솔루션) 프레임워크로 구조화하여 설계 세계관을 일치시키는 과정이 필수적이다.
3. **린터를 통한 코드 레벨 강제**: 파일 명명 규칙부터 아키텍처까지 린터로 강제함으로써 AI가 생성하는 코드의 품질과 멱등성을 보장한다.
4. **조직 맞춤형 평가(Evaluation) 프레임워크**: 엔터프라이즈 환경에서는 범용 지표가 아닌 조직의 특성과 문화에 맞는 자체 평가 프레임워크 구축이 중요하다.

## 세부 내용

### 1. 엔터프라이즈 AX와 FDE의 역할

- **출연진**: 엔터프라이즈 AX 전문 기업 스페이스와이의 황현태 대표, DIO의 김지운 FDE
- **FDE(Forward Deployed Engineer)**: 고객사에 직접 파견되어 제로투원을 함께하는 파견형 엔지니어
  - 고객의 막연한 요구사항을 기술적으로 정의하고 문제 정의를 수행
  - 주 2~3회 방문, 오전/오후 미팅을 통해 지속적 소통
- **AX(AI Transformation)** 트렌드가 국가적 변화 수준으로 확산 중
- 엔터프라이즈 AX 경험치가 아직 부족한 시장이므로 경험 공유가 중요

### 2. 하네스 엔지니어링과 멱등성의 개념

- **멱등성(Idempotency)**: 같은 입력을 넣으면 항상 같은 결과가 나오는 성질
- 하네스 엔지니어링의 핵심 목표는 AI 모델에 관계없이 필연적이고 멱등성 있는 결과물을 도출하는 것
- **검증 실험**: 배달 플랫폼(고객용, 기사용, 음식점용, 어드민) 4개 소프트웨어를 클로드/코덱스/제미나이 3개 모델에 각각 시킨 결과(총 12개), 하네스 엔지니어링 적용 시 모두 동일한 아웃풋 도출
- 프롬프트 엔지니어링만으로는 일관성을 강제할 수 없기 때문에 시스템적 접근(하네스)이 필수

### 3. 6단계 하네스 엔지니어링 프로세스

전체 프로세스는 6단계로 구성:

| 단계 | 내용 | 설명 |
|------|------|------|
| 1단계 | 요구사항 수집 | 고객의 비정형적 요구를 자유롭게 수집 |
| 2단계 | 플랜(Plan) | 미팅 로그 정리, CPS 문서 작성 |
| 3단계 | 설계 분석 | 원칙 수립, 개념 정의, 아키텍처 설계 |
| 4단계 | 코드 레벨 설계 | 도메인 드리븐 디자인 + 린터 강제 |
| 5단계 | 코드 생성 및 검증 | AI 코드 생성 후 린터 자동 검증 |
| 6단계 | 평가(Evaluation) | 조직 맞춤형 품질 모니터링 |

### 4. 구조화된 기획과 CPS 프레임워크

- **CPS(Context-Problem-Solution)** 프레임워크:
  - **Context**: 팀이 공유하는 배경 맥락
  - **Problem**: 고객이 겪고 있는 문제
  - **Solution**: 제시할 기술적 해결책
- 미팅 로그를 종합하여 하나의 CPS 문서로 수렴
- CPS 문서는 고객과 개발팀 간의 "세계관 일치" 도구
- **문서 전달 시점**: POC 기간 중 2회 (1차 스펙 확정 시, 프로젝트 완료 후 역기획)
- 문서는 Git 저장소에서 버전 관리되며 지속 업데이트
- 마크다운으로 작성 후 LaTeX 템플릿으로 PDF 빌드하여 고객에게 전달

### 5. 설계 문서의 핵심 구성 요소

- **원칙(Principles) 수립**: 프로젝트별 대전제 (예: Human-in-the-loop, 환각 방지, 로그 기록 등)
- **개념 정의(Definitions)**: 도메인 개념의 하이어라키 정의
- **구조(Structure) 설계**: 개념의 위계에 따른 아키텍처 설계
- **유저 멘탈 모델** 포함
- 이 세 단계(원칙 → 정의 → 구조)를 거치면 필연적인 방향의 코드가 도출

### 6. 팀 내 멘탈 모델 일치와 협업

- 코드 컨벤션보다 **멘탈 모델 일치**에 집중
- 모든 산출물은 GitHub 팀 저장소에 오픈, 로그는 Notion에 기록
- 도구: GitHub, Notion, Slack 세 가지만 사용
- 고정 요일에 팀 내 설계 리뷰 수행 (집단 지성 형성)
- 고객사에게도 설계 세계관을 공유하여 커뮤니케이션 품질 향상

### 7. 린터를 활용한 코드 레벨 강제화

- **파일 명명 규칙 강제**: 도메인 관점에서 복수형 페이지명 사용 (예: `restaurants_page`), "detail", "list" 등의 접미사 사용 금지
- **임포트 규칙 강제**: 알파벳 순서, 임포트 가능/불가 파일 구분, 배럴 파일 규칙
- **커밋 시 자동 린터 실행**: 커밋을 시도하면 린터가 자동으로 돌아가며, 위반 시 AI가 자동 수정
- 파일명이 강제되면 하위 클래스, 헬퍼 메소드 명칭도 자연스럽게 강제
- **장점**: 어떤 AI 모델을 사용해도 동일한 코드 아웃풋, 인간이 읽기 쉬운 코드
- **단점**: AI가 자연스럽게 생성하기 편한 스타일과 다를 수 있어 토큰 비효율 가능성
  - 그러나 유지보수와 인간 협업의 가치가 이를 상쇄

### 8. 유지보수를 고려한 설계의 가치

> "바이브 코딩으로 엔터프라이즈에 딸깍한 다음에 그거 유지보수까지 넘어간 사례는 없다."

- 엔터프라이즈 AI 시스템은 결국 유지보수 단계로 넘어감
- 유지보수를 일반 SI 팀이 받을 수 있으므로 **Human-Readable한 코드**가 핵심
- 하네스가 잘 세팅되어 있으면 새로운 개발자가 투입되어도 규칙 문서를 통해 빠르게 학습 가능
- 코드에 버그 발생 시, 해당 코드의 역할이 명확하게 강제되어 있으면 통째로 삭제 후 재구현 가능 (AI 시대에 더욱 용이)

### 9. 조직 맞춤형 평가(Evaluation) 시스템

- 기본 4가지 AI 평가 지표: 맥락 적합성, 결과 정확성, 소스 데이터 적절성, 누락 여부
- 하지만 엔터프라이즈에서는 **조직별 맞춤 평가**가 필요:
  - 어떤 조직은 "100번 중 1번 틀려도 답변하는 것"을 선호
  - 어떤 조직은 "20번 틀려도 답변 안 하는 것"을 선호
  - 조직 문화와 비즈니스 목적에 따라 허용 오류 성격이 다름
- **"에이전트 도그(Agent Dog)"**: DataDog처럼 AI 에이전트의 품질을 매일 모니터링하는 시스템
- 프로젝트별 품질 관리 대시보드를 별도 제작하여 고객사에 납품
- 공격(하네스)과 수비(평가)가 모두 갖춰져야 엔터프라이즈 AI 빌딩이 완성

### 10. 멱등성에 대한 원체험 -- 하드웨어 프로젝트 경험

- 김지운 FDE가 하드웨어 프로젝트에서 펌웨어(C 코드)를 구현하다 문제 발생
- 전문가의 조언: "포맷을 해오라" -- 제로 상태에서 다시 시작해야 결과물로 가는 단계가 멱등해짐
- 이 경험이 현재 소프트웨어 엔지니어링에서 "필연적 방향의 코드"를 추구하는 원동력이 됨
