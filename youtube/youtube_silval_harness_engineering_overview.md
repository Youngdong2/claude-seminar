## 핵심 요점 (Key Points)

1. **프롬프트는 부탁, 하네스는 강제**: 프롬프트 엔지니어링과 컨텍스트 엔지니어링만으로는 AI의 규칙 위반을 막을 수 없다. 하네스 엔지니어링은 시스템적으로 실수를 구조적으로 불가능하게 만든다.
2. **4가지 기둥**: 컨텍스트 파일(CLAUDE.md), CI/CD 게이트(린터/Hook), 도구 경계(최소 권한), 피드백 루프(가비지 컬렉션)가 하네스의 핵심 구성 요소다.
3. **에이전틱 + 하네스의 결합**: 에이전틱 엔지니어링(말 훈련)과 하네스 엔지니어링(마구 제작)은 대체 관계가 아닌 상호보완적 관계다. 둘 다 필요하다.
4. **역할의 상향 이동**: 개발자의 역할이 "코드를 쓰는 사람"에서 "AI가 일할 환경을 설계하는 사람"으로 진화하고 있다.

## 세부 내용

### 1. AI 활용 4가지 축 프레임워크

AI를 활용하는 방법을 4가지 상호보완적 축으로 정리:

| 축 | 핵심 질문 | 역할 |
|----|-----------|------|
| **프롬프트 엔지니어링** | AI에게 어떻게 말할 것인가? | AI의 의도를 정확히 전달 |
| **컨텍스트 엔지니어링** | AI에게 어떤 정보를 줄 것인가? | 참조할 지식 체계 설계 |
| **하네스 엔지니어링** | AI가 무엇을 할 수 있고 없는가? | 실수할 수 없는 환경 설계 |
| **에이전틱 엔지니어링** | AI가 어떻게 자율적으로 일하는가? | 추론 루프와 멀티에이전트 조율 |

이 네 가지는 순서대로 졸업하는 것이 아니라, 전부 다 필요한 상호보완적인 축이다.

### 2. 프롬프트와 컨텍스트의 한계

- **프롬프트 엔지니어링의 천장**: 아무리 정교하게 요청해도, 프로젝트 기술 스택/코드 구조/DB 스키마를 모르면 좋은 코드가 나올 수 없음
- **컨텍스트 엔지니어링**: AI에게 프로젝트 구조, 기존 코드, API 문서, 디자인 규칙 등을 함께 제공
  - Anthropic의 정의: "AI가 일할 때 필요한 정보를 적절하게 골라서 제공하는 기술"
  - 핵심: 많이 주는 것이 아니라 **지금 필요한 것만 정확하게** 주는 것
- **그래도 해결 안 되는 문제**: AI가 정보를 다 알고 있는데 엉뚱한 짓을 하는 경우 (예: 결제 시스템에서 DB 스키마를 마음대로 변경, 신용카드 번호를 로그에 기록)
  - 이것은 정보의 문제가 아닌 **규칙과 울타리의 문제**

### 3. 말(Horse)과 마구(Harness) 비유

AI 에이전트를 거대한 말에 비유:

| | 에이전틱 엔지니어링 | 하네스 엔지니어링 |
|---|---|---|
| **비유** | 말을 훈련시키는 기술 | 가죽끈, 고삐, 수레를 만드는 기술 |
| **집중** | 자율 워크플로우, 에이전트 생성 | 가드레일, 테스트 게이트, 제약 설정 |
| **다루는 것** | AI가 어떻게 생각하는가 | AI가 무엇을 할 수 있고 없는가 |
| **실패 시** | 프롬프트 변경, 추론 루프 조정 | 규칙과 테스트 자동 추가 |
| **인간의 역할** | 위임자, 감독자 | 설계자, 경계 설정자 |

> "말을 아무리 잘 훈련시켜도, 마구 없이는 밭을 갈 수 없다."

### 4. 하네스 엔지니어링의 정의와 핵심 철학

- **Martin Fowler의 정의**: AI 에이전트가 자율적으로 일하되, 동시에 안전하게 통제할 수 있는 환경을 만드는 것
- **역사적 배경**: "Test Harness"는 1970년대부터 소프트웨어 엔지니어링에 존재했으나, 전통 소프트웨어는 예측 가능(같은 입력 = 같은 결과)했기에 별도 하네스 엔지니어가 불필요했음. LLM은 예측 불가능(환각, 컨텍스트 분실)하므로 이 개념이 새로운 의미를 획득

**핵심 철학:**
> "에이전트가 규칙을 어겼을 때, '더 잘해 봐'라고 프롬프트를 고치는 게 아니다. 그 실패가 구조적으로 반복 불가능하도록 하네스를 고치는 것이다."

- 예시: AI가 프론트엔드 코드에서 DB를 직접 호출
  - 프롬프트 접근: "DB를 직접 호출하지 마" 문장 추가 -> 다음번에 또 실수 (프롬프트는 부탁)
  - 하네스 접근: 아키텍처 테스트 추가, 프론트엔드 폴더에서 DB 임포트 시 빌드 실패 -> 구조적으로 불가능

### 5. 하네스의 4가지 기둥

#### 기둥 1: 기계가 읽는 컨텍스트 파일

- CLAUDE.md, AGENTS.md, .cursorrules 등
- 단순한 문서가 아닌 **AI가 실행하는 런타임 설정 파일**
- 코드 저장소 안에 위치, AI 에이전트가 작업 시작 시 가장 먼저 읽음
- 예시 규칙: 새 라이브러리 도입 금지, 기존 API 패턴 준수, DB는 ORM을 통해서만 접근
- 한번 설정하면 모든 작업에 자동 적용 (매번 프롬프트 반복 불필요)

#### 기둥 2: 결정론적 CI/CD 게이트

- 규칙을 파일에 써 놓는 것만으로는 불충분 (AI는 규칙을 읽고도 어길 수 있음)
- **린터(Linter)**: 코드 맞춤법 검사기, 규칙 위반 시 자동 에러
- **구조적 테스트**: "이 폴더의 코드는 저 폴더의 코드를 임포트할 수 없다" 등 의존성 규칙 강제
- **Pre-commit Hook**: 코드 저장 전 자동 검사
- **핵심 메커니즘 -- 자동 교정 루프**: CI가 실패하면 에이전트가 스스로 코드를 수정하고 다시 시도. 인간 개입 불필요

#### 기둥 3: 명시적 도구 경계 (최소 권한 원칙)

AI 에이전트의 접근 범위와 권한을 명확히 제한:

| 영역 | 허용 | 차단 |
|------|------|------|
| 파일 시스템 | src/ 폴더 읽기/쓰기 | config/ 폴더 쓰기 |
| API | 내부 API 호출 | 외부 서비스 호출 |
| 데이터베이스 | SELECT | DROP TABLE |
| 터미널 | 화이트리스트 명령만 | 기타 전부 차단 |

> "프롬프트는 부탁이고, 도구 경계는 물리적 차단이다. 부탁은 어길 수 있지만 제약은 어길 수 없다."

#### 기둥 4: 지속적 피드백 루프 (가비지 컬렉션)

- Martin Fowler가 명명한 "가비지 컬렉션" 개념
- AI 에이전트는 기존 코드의 나쁜 패턴을 그대로 따라 하므로, 나쁜 패턴이 눈덩이처럼 불어남
- **자동 청소 시스템** 필요:
  - 코딩 규칙 위반 자동 감지
  - 중복 코드 발견
  - 리팩토링 PR 자동 생성
  - 데드 코드 자동 제거
  - 아키텍처 위반(안티패턴) 주기적 체크
- **하네스의 진화적 특성**: 에이전트가 실수할 때마다 새로운 규칙(린터 규칙, 테스트, 제약)이 추가되어 시스템이 점점 더 견고해짐

### 6. 하네스 시스템 작동 구조 (4단계 파이프라인)

| 단계 | 역할 | 비유 |
|------|------|------|
| **1. 분류기(Router)** | 요청을 분류 (단순 질문 vs 코드 작업), 모호한 요청은 되묻기 | 고삐의 방향 전환 |
| **2. 컨텍스트 관리자** | 작업에 필요한 파일과 규칙만 선별 제공 (전체 코드가 아닌 해당 구역만) | 가림막 |
| **3. 실행 루프** | 코드 작성 -> 테스트 -> 실패 시 에러 메시지를 AI에게 피드백 -> 수정 -> 반복 (통과까지) | 하네스의 심장 |
| **4. 워커 격리** | 코드 작성 AI와 코드 검토 AI의 역할 완전 분리 | 역할 분담 |

**실제 적용 예시 (토스 API 결제 연동)**:
1. 라우터가 요청을 검증/분류
2. 컨텍스트 매니저가 토스 SDK 문서와 제약 사항 제공
3. 실행 루프가 코드 생성 -> 테스트 돌려 검증
4. 사용자가 결과를 보기 전에 AI가 스스로 오류를 수정

### 7. 실제 사례: OpenAI 팀의 하네스

- 2026년 2월, OpenAI 공식 블로그 발표: **엔지니어 3명이 코드를 한 줄도 직접 쓰지 않고 5개월 만에 소프트웨어 제품 배포**
- 이들이 한 일은 코드 작성이 아니라 **하네스 시스템 설계**:

| 하네스 구성 요소 | OpenAI 팀의 적용 |
|---|---|
| 컨텍스트 파일 | AGENTS.md 작성, AI 지침서 설계 |
| CI/CD 게이트 | 린트, 테스트, 훅으로 자동 검증 파이프라인 구축 |
| 도구 경계 | AI 에이전트의 접근 범위/권한 사전 설정 |
| 피드백 루프 | AI가 코딩 -> 결과 리뷰 -> 규칙 보강 순환 |

> "인간은 조종한다(harness). 에이전트는 실행한다."

### 8. 역할의 진화

| 단계 | 역할 | 설명 |
|------|------|------|
| 프롬프트 엔지니어 | AI의 의도를 정확히 전달하는 사람 | 프롬프트 작성 능력 |
| 컨텍스트 아키텍트 | AI가 참조할 지식 체계를 설계하는 사람 | 정보 설계 능력 |
| 하네스(플랫폼) 엔지니어 | AI가 실수할 수 없는 환경을 만드는 사람 | 시스템 설계 능력 |
| 에이전트 오케스트레이터 | 다중 AI 에이전트를 지휘하는 사람 | 오케스트레이션 능력 |

- 코딩 능력이 필요 없어지는 것이 아니라, **더 높은 차원의 능력**이 요구됨
- 직접 공을 차는 선수에서 전술을 짜고 팀을 운영하는 **감독**으로 상향 이동
- 비개발자도 마찬가지: AI를 효과적으로 쓰려면 자기 분야의 전문성이 더욱 중요

> "에이전트가 규칙을 어겼을 때, '더 잘해 봐'라고 프롬프트를 고치는 게 아닙니다. 그 실패가 구조적으로 반복 불가능하도록 하네스를 고치는 겁니다."

> "프롬프트는 부탁이지 강제가 아니다. 아키텍처 테스트를 추가해서 프론트엔드 폴더에서 DB를 임포트하려는 순간 빌드가 실패하도록 만들어 버리는 것. 이것이 하네스의 철학이다."

> "린터가 빨간 불을 켜면 에이전트가 자동으로 코드를 고치고 다시 시도합니다. 이 자동 교정 루프가 하네스의 핵심 메커니즘입니다."

> "AI 에이전트가 실수했을 때 프롬프트를 고치지 마세요. 하네스를 고치십시오."

> "개발자든 비개발자든, AI 시대에 우리의 역할은 축소되는 게 아닙니다. 상향 이동되는 겁니다. 직접 공을 차는 선수에서 전술을 짜고 팀을 운영하는 감독으로 한 단계 올라가는 겁니다."

> "말을 아무리 잘 훈련시켜도 마구 없이는 밭을 갈 수 없고, 아무리 정교한 마구라도 말이 없으면 수레는 움직이지 않는다."
