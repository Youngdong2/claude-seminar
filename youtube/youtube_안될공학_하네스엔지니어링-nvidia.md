## 핵심 요점 (Key Points)

1. **프롬프트 엔지니어링 -> 컨텍스트 엔지니어링 -> 하네스 엔지니어링** -- AI 활용 패러다임이 단순 입력 최적화에서 전체 실행 구조 설계로 진화하고 있다.
2. **하네스 엔지니어링 = 모델 바깥의 실행 시스템 설계** -- Planner, Generator, Evaluator 등 역할을 분리한 멀티 에이전트 구조가 동일 모델에서 극적인 성능 향상을 이끌어낸다.
3. **소프트웨어와 하드웨어가 동일한 방향으로 분화** -- 에이전트의 역할 분리(소프트웨어)와 GPU/CPU/메모리의 계층 분리(하드웨어)가 같은 오케스트레이션 원리를 따른다.
4. **NVIDIA Dynamo 1.0은 에이전트 인프라 계층** -- 에이전트 무리를 데이터센터 규모로 운영하기 위한 서빙/오케스트레이션 소프트웨어 스택이다.
5. **AI 산업의 경쟁축이 "모델 성능"에서 "운영 구조와 오케스트레이션"으로 이동** -- 벤치마크 점수보다 하네스 설계, 장기 세션 운영, 툴 활용 안정성이 새로운 평가 기준이 된다.

## 세부 내용

### 1. 프롬프트 -> 컨텍스트 -> 하네스: 패러다임의 진화

**프롬프트 엔지니어링 시대:**
- AI에게 "말을 잘 거는 것"에 집중
- 역할 지정, 말투 설정 등 입력 문장 최적화

**컨텍스트 엔지니어링 시대 (Anthropic 2025년 9월):**
- 프롬프트만으로는 한계 -- 어떤 맥락을 어떤 타이밍에, 어떤 형태로 제공하느냐가 핵심
- 컨텍스트 윈도우라는 유한한 리소스 안에서 정보를 큐레이션하는 기술
- "그냥 막 때려넣지 마라" -- Anthropic 블로그의 핵심 메시지

**하네스 엔지니어링 시대 (Anthropic 2025년 11월 ~ 2026년):**
- 여러 컨텍스트 창을 넘나드는 롱러닝 에이전트 문제 등장
- 한 번의 긴 대화가 아니라, 작업을 나누고 중간 상태를 저장하고 다음 세션에 넘기는 구조
- 세션 간 핸드오프, 점진적 진척이 가능한 전체 실행 구조 설계

### 2. Anthropic의 하네스 설계: Planner-Generator-Evaluator

Anthropic은 에이전트 코딩 성능의 핵심이 **세 가지 에이전트 역할 분리**에 있다고 발표했다.

| 역할 | 기능 |
|------|------|
| **Planner** | 작업 계획 수립, 작업 분해 |
| **Generator** | 실제 코드/콘텐츠 생성 |
| **Evaluator** | 결과 검증, 피드백 제공 |

- 이 세 역할이 에이전트 간 왔다 갔다 하며 반복적으로 개선
- 특히 프론트엔드 디자인에서 효과적: 초기 "AI스러운" 결과물이 반복 루프를 통해 극적으로 개선됨

**실제 사례 -- 벚꽃 축제 페이지:**
- 초기 버전 대비 10라운드 피드백 후 감성적 품질이 크게 향상

**실제 사례 -- 2D 레트로 게임 제작 도구:**

| 구분 | 솔로 (하네스 없음) | 풀 하네스 |
|------|-------------------|----------|
| 소요 시간 | 20분 | 6시간+ |
| 비용 | $9 | $200 |
| 결과 품질 | 기본적 수준 | 스프라이트 에디터, AI 게임 디자인 등 정교한 품질 |

- 동일 모델(Claude Opus 4.5)이지만 하네스 유무에 따라 결과 차이가 극적

### 3. Anthropic의 정의: 하네스(Harness) / 스캐폴드(Scaffold)

> 하네스 = 모델이 에이전트처럼 행동하도록 해 주는 시스템

구체적으로:
- 입력 처리, 툴 호출 조율, 결과 반환
- 모델 바깥에 있는 실행 시스템
- 실패 복구, 테스트 실행, 중간 결과 저장 등 포함

**에이전트 성능 평가의 재정의:**
- 기존: "이 AI 모델이 얼마나 잘하냐" (벤치마크 점수)
- 변화: "이 모델 + 하네스가 어떻게 잘 구성됐냐"를 함께 평가

### 4. 하드웨어의 동일한 분화 흐름

소프트웨어에서 에이전트 역할을 분리하는 것처럼, 하드웨어도 동일한 오케스트레이션 방향으로 진화하고 있다.

**NVIDIA의 하드웨어 분화:**
- **Rubin CPX / Grace LPX**: 컴퓨팅 계층을 용도별로 분리
- **HBM / KV Cache / SSD**: 메모리 계층을 역할별로 나눔
- **BlueField DPU**: 스토리지 계층을 별도로 분리
- **CPU의 재부상**: GPU는 병렬 연산, CPU는 오케스트레이션 중간 조율을 담당

**Speculative Decoding -- 하드웨어 역할 분리의 상징적 사례:**
- 작은 Draft 모델이 후보 토큰을 먼저 생성
- 큰 Target 모델이 이를 병렬로 검증
- 단순 가속이 아니라 "역할을 분리한 후 검증하는 구조"
- Anthropic의 멀티 에이전트 하네스 구조(Generator + Evaluator)와 본질적으로 동일한 원리

### 5. NVIDIA Dynamo 1.0: 에이전트 인프라 계층

**Dynamo는 단순한 추론 서버가 아니다:**
- 에이전트 무리가 실제 서비스 규모로 배치되어 운영될 수 있는 운영 체제
- 멀티노드 환경에서 모델 서빙, GPU 자원 관리, 추론 요청 오케스트레이션
- AI Factory(거대 데이터센터)에서 여러 AI가 에이전틱하게 각자 역할을 수행하며 돌아가는 전체 운영 계층

**핵심 관계:**
- 하네스 엔지니어링 = 에이전트의 업무 프로세스 설계 (소프트웨어)
- Dynamo = 그것을 대규모로 굴리는 인프라 계층 (하드웨어/서빙)

### 6. AI 산업 경쟁축의 이동

**모델 평가 지표의 변화:**
- 단순 벤치마크 -> 장기 컨텍스트 저장 능력, 툴 사용 안정성, 에이전트 간 컨텍스트 핸드오프, 피드백 반영 능력
- 하네스 자체를 함께 평가하는 새로운 프레임워크 필요

**경쟁 포인트의 전환:**
- 기존: "엄청나게 큰 모델을 만들었어요" (GPT-5 등)
- 현재: "주어진 모델을 얼마나 잘 쓸 수 있게 만드느냐"
- 모델 점수 경쟁 -> 에이전트 적합성 경쟁

**SaaS 기업의 생존 전략:**
- 사람이 UI를 클릭하는 형태의 SaaS -> API 호출 중심의 AI-friendly 구조로 전환 필요
- 권한 구조가 명확하고, API를 통해 AI가 자율적으로 활용할 수 있는 소프트웨어 기업이 경쟁력 확보
- 서비스 기업의 가치가 "업무 하네스 설계"로 이동

**인프라 경제의 변화:**
- 단순 연산 성능 -> 긴 장기 세션을 안정적으로 운영할 수 있는 데이터센터 구축
- GPU뿐 아니라 메모리, 스토리지, 오케스트레이션 소프트웨어가 하나로 묶이는 통합 설계
