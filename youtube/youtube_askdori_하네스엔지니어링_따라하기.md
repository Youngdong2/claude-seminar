## 핵심 요점 (Key Points)

1. **프롬프트 vs 하네스**: 프롬프트 엔지니어링은 매번 맥락을 설명하는 "도구 사용", 하네스 엔지니어링은 AI가 일할 환경 자체를 설계하는 "위임 구조"다.
2. **4가지 구성요소**: 헌법(규칙), 작업 구조(지시서), 검증(품질 기준), 실행 루프(반복 워크플로우)로 구성된다.
3. **레포지토리 하네스 + 애플리케이션 하네스**: 회사 전체 규칙(취업규칙)과 프로젝트별 매뉴얼을 분리하여 설계한다.
4. **본질은 경영학이다**: 하네스 엔지니어링은 피터 드러커의 MBO(목표에 의한 관리)와 본질적으로 같다. AI라는 팀원에게 위임하기 위한 조직 설계다.
5. **AI는 나를 1인 조직으로 만든다**: 하네스를 통해 개인이 팀의 아웃풋을 낼 수 있게 되며, 51번째 작업의 출발점은 50번째보다 훨씬 월등해진다.

## 세부 내용

### 1. 하네스 엔지니어링이란?

- **정의**: AI에게 잘 일할 환경을 설계해 주는 것
- **프롬프트 엔지니어링과의 차이**:

| | 프롬프트 엔지니어링 | 하네스 엔지니어링 |
|---|---|---|
| **방식** | 매번 필요한 맥락을 새로 설명 | 환경을 미리 설계 |
| **결과** | 일관된 결과 얻기 어려움 | 구조적으로 일관된 품질 |
| **비유** | 그때그때 잘 요청하는 기술 | AI가 일하는 환경 자체를 설계 |

### 2. 하네스 엔지니어링의 4가지 구성요소

| 구성요소 | 역할 | 비유 |
|----------|------|------|
| **헌법 (Constitution)** | LLM이 따라야 할 규칙 문서 | "우리 팀은 이렇게 일한다" |
| **작업 구조 (Task Structure)** | 무엇을 어떻게 만들지 정의 | 작업 지시서 |
| **검증 (Verification)** | 결과가 맞는지 체크하는 기준 | "이 결과물이 괜찮은지 뭘 보고 판단?" |
| **실행 루프 (Execution Loop)** | 수정 → 검증 → 반복의 워크플로우 | 만족할 때까지 반복 |

추가로 필요한 것:
- **작업 저장소**: 로컬 폴더 + Git 연동
- **참고 자료**: 변수가 많고 복잡한 작업에 필요한 레퍼런스

### 3. 레포지토리 하네스 vs 애플리케이션 하네스

| | 레포지토리 하네스 | 애플리케이션 하네스 |
|---|---|---|
| **범위** | 저장소 전체에 적용 | 프로젝트/앱별 적용 |
| **내용** | 문서 구조, 팀 규칙, 코드 린터 | 기능 명세, 프로젝트별 규칙 |
| **비유** | 회사의 취업 규칙 | 팀 프로젝트 매뉴얼 |
| **순서** | 먼저 정의 | 나중에 정의 |

> 단, 초보자는 "뭘 만들고 싶다"가 먼저이므로 앱 레벨부터 시작해도 괜찮다.

### 4. 실습: 사주 분석 웹앱 만들기 (따라하기)

#### 준비물
- Claude Code 또는 Codex (둘 중 하나)
- Git (Mac은 기본 설치, Windows는 별도 설치)
- Python 또는 사용하는 언어

#### 실습 흐름

**Step 1: 구조 잡기 (아이디에이션 — Claude 사용)**
1. OpenAI의 하네스 엔지니어링 아티클 페이지에서 폴더 구조 복사
2. Claude에 붙여넣기 + "나는 사주분석 앱을 만들고 싶어. 하네스 엔지니어링을 통해 만들고 싶어. 같이 하나하나 의논해볼까?" 입력
3. Claude가 선택지를 제공하며 하나씩 협의 → 문서 초안 완성

> 팁: 아이디에이션은 Claude가 편함 (선택지 제공 + 구조 기반 순차 완성)

**Step 2: 1차 문서 점검**
- "여태까지 쓴 문서 다 검토해서 논리적으로 일관적인지, 모순이 없는지 재검토해줘"
- 예: "사용자 데이터 서버 저장 안 한다" vs "DB 기록이 쌓인다" 모순 발견

**Step 3: 마크다운 문서 다운로드**
- Claude의 아티팩트를 ZIP 파일로 일괄 다운로드 → 특정 폴더에 배치

**Step 4: 레포지토리 하네스 구현 (Codex 사용)**
- "이 폴더에서 레포지토리 하네스 엔지니어링을 구현하고 싶어. 파일들을 모두 읽은 후 같이 이야기해보자"
- Codex가 파일 읽고 → 레포지토리 레벨 정의 협의

**Step 5: 헌법 함께 만들기**
- **중요**: 헌법은 AI에게 통째로 맡기지 말고, 나와 함께 합의하면서 작성
- 헌법이 흔들리면 모든 문서가 흔들림

**Step 6: 2차 문서 평가 (다중 관점)**
- "네가 시니어 개발자라면 이 문서를 어떻게 평가할 거 같아?"
- 소프트웨어 엔지니어, 보안 담당자, 초보 개발자 관점에서 반복 평가
- 점수 기반 평가를 요청하면 더 정교한 피드백 가능

**Step 7: 암묵지 좁히기**
- 내 머릿속에 있지만 AI에게 전달 안 된 지식을 명시화
- 예: "교육용이니까 짧고 읽기 쉬워야지" → "500줄 이하로 짜라"고 명시
- AI에게 말 안 하면 10줄로 끝낼 수 있는 걸 300줄로 늘릴 수 있음

**Step 8: 실행 루프 + 결과 확인**
- Gradio로 웹 확인 → 피드백 → 수정 → 만족할 때까지 반복

### 5. 하네스 엔지니어링 = 경영학 (피터 드러커의 MBO)

#### 두 가지 나쁜 상사 유형

| 유형 | 문제 |
|------|------|
| **방임형** | "AI는 유능하니까 알아서 잘하겠지" → 맥락 없이 던짐 → 엉뚱한 결과 |
| **지시형** | 처음부터 모든 걸 다 설명 → AI가 더 나은 방법 찾을 공간 없음 → 상사 경험의 한계 = 팀 결과의 한계 |

#### 올바른 위임 (MBO와 하네스의 대응)

피터 드러커의 MBO(Management by Objective) 5단계:

| MBO 단계 | 하네스 엔지니어링 대응 |
|----------|----------------------|
| 1. 목표 설정 | 내 수요에 대해 알고 큰 목표 정하기 |
| 2. 팀/개인 단위 쪼개기 (캐스케이딩) | AI와 함께 지식을 나누고 일 쪼개기 |
| 3. 개인 목표 합의 | 구체적 목표를 AI와 합의 |
| 4. 실행 및 모니터링 | 중간중간 맞았어/틀렸어 피드백 |
| 5. 성과 평가 | 내 기준에 맞는지 평가 → 통과까지 반복 |

### 6. AI는 나를 1인 조직으로 만든다

- **기존 조직의 한계**: 암묵지가 사람 머릿속에 분산 → 사람 나가면 지식 사라짐 → 커뮤니케이션 비용 증가
- **AI의 변화**: 인지적 병목 제거 (컨텍스트 윈도우: A4 1.5장 → 소설책 6~7권, 2~3년 만에)
- **잭 샤피로(Jack Shapiro)의 "10x Lawyer"**:
  - 대형 로펌: 파트너 머릿속 수천 개 딜 경험 + 어소시에이트 노트에 분산 → 사람 나가면 사라짐
  - 하네스를 가진 개인: 매 작업이 저장소에 축적 → 헌법 진화, 검증 기준 정교화 → 실행 루프 가속
  - **51번째 작업의 출발점은 50번째보다 훨씬 월등**

#### 하네스의 본질

> 뛰어난 개인의 판단력과 암묵지를 어떻게 조직의 자산으로 만드는가?

| 구성요소 | 역할 |
|----------|------|
| 헌법 | 코어 가치와 원칙을 외부화 |
| 작업 구조 | 판단 패턴을 AI가 재사용 가능한 형태로 |
| 검증 | 검증 기준을 기계가 대신 집행 |
| 실행 루프 | 매 작업마다 암묵지가 저장소에 축적 |

→ 코어 가치 → 합의 → 위임 → 축적의 과정
→ 저장소는 나의 경험이 구조화된 형태로 보존되는 공간
→ **판단력이 곧 해자(moat)**
