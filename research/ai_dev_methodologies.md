## 1. 개요: AI 시대 개발 방법론의 등장 배경

### 패러다임 전환의 시작

2025년 초, Andrej Karpathy가 "Vibe Coding"이라는 용어를 만들면서 AI 보조 개발 혁명이 본격적으로 시작되었다. Y Combinator 2025년 겨울 배치의 25%가 코드베이스의 95%를 AI로 생성했다고 보고될 정도로 AI 코드 생성은 폭발적으로 성장했다.

그러나 허니문 기간은 오래가지 않았다. AI가 생성한 코드의 품질 문제, 기술 부채, 유지보수 불가능한 프로젝트가 속출하면서, 업계는 인간과 AI가 코드를 어떻게 협업해야 하는지를 근본적으로 재고하기 시작했다.

### 왜 방법론이 필요한가?

2025년 이전, 대부분의 개발자는 AI를 "고급 자동완성(fancy autocomplete)"으로 사용했다. 주석을 타이핑하면 제안이 나오고, 수락하거나 거부했다. 단순했다.

그러다 **에이전틱 코딩(Agentic Coding)** 이 등장했다 -- AI가 계획을 세우고, 다단계 작업을 실행하고, 전체 기능을 작성할 수 있게 되었다. 갑자기 병목이 바뀌었다. 코드를 작성하는 것이 어려운 게 아니라, **AI에게 무엇을 작성할지 알려주는 것**, 그리고 **AI가 실제로 원하는 대로 했는지 확인하는 것**이 어려운 일이 되었다.

이 전환은 다음과 같은 새로운 개발 방법론의 등장을 촉발했다:

| 시기 | 사건 | 영향 |
|------|------|------|
| 2025.02 | Karpathy "Vibe Coding" 명명 | AI 코딩의 대중화, 문화적 전환점 |
| 2025 중반 | AI 생성 코드의 품질/보안 문제 부각 | 구조화된 방법론의 필요성 대두 |
| 2025 하반기 | SDD, BMAD 등 프레임워크 등장 | Vibe Coding의 한계에 대한 업계 대응 |
| 2026 초 | TDD + AI, Context Engineering 부상 | 성숙한 AI 개발 워크플로우의 정립 |

## 2. TDD -- AI 시대의 테스트 주도 개발

### 정의

AI 시대의 TDD는 전통적인 Red-Green-Refactor 사이클을 AI 에이전트와 결합한 개발 방법론이다. **인간이 실패하는 테스트를 먼저 작성하고, AI 에이전트가 테스트를 통과하는 코드를 구현하는** 방식으로, AI의 비결정적(non-deterministic) 출력을 결정적(deterministic) 테스트로 제어한다.

### 핵심 원칙

1. **테스트가 우리(cage)다**: AI 에이전트의 혼란스러운 행동을 통제하는 "우리" 역할을 한다. 테스트는 결정적이지만, 에이전트는 비결정적이다.
2. **인간이 테스트를 작성하고, AI가 구현한다**: AI가 코드와 테스트를 동시에 작성하면, AI는 자신의 결함 있는 로직을 확인하는 약한 테스트를 "치팅"으로 작성한다.
3. **한 번에 하나의 테스트**: AI에게 모든 테스트를 한꺼번에 생성하게 하면 얕고 중복된 테스트가 나온다. 한 번에 하나의 행동(behavior)에 대한 테스트만 작성한다.
4. **테스트를 수정하여 통과시키지 않는다**: 이 규칙 없이는 에이전트가 구현이 맞지 않을 때 테스트 어서션을 조정해버린다.

### AI 시대 TDD 워크플로우

```
1. [인간] 비즈니스 요구사항을 정의하는 실패 테스트(Red) 작성
2. [AI 에이전트] 테스트를 통과하는 최소 코드(Green) 구현
3. [인간] 통과 코드를 수동 감사 (레이턴시, 메모리 등)
4. [AI 에이전트] 통과 상태를 유지하며 코드 정리(Refactor)
5. 반복
```

### AI + TDD의 핵심 인사이트

> "에이전트가 Red에서 Green으로 가는 것을 지켜보는 것은, 코드의 모든 줄을 읽지 않고도 신뢰를 확보하는 방법이다." -- LoreAI

- **Red-to-Green 전환이 검증 신호**: 에이전트가 테스트를 수정하지 않고 구현을 작성하여 테스트가 통과하면, 그 사이클을 속이기는 매우 어렵다
- **리뷰 워크플로우의 변화**: 모든 구현 코드를 읽는 대신, 테스트 제목을 훑어보고, Red-to-Green 전환을 신뢰하며, 완료된 청크를 QA한다
- **선순환 사이클**: LLM은 코드베이스에서 보는 패턴을 복제한다. TDD로 만든 잘 구조화된 코드는 미래 AI 생성 코드의 품질도 높인다

### 장단점

| 장점 | 단점 |
|------|------|
| AI 환각(hallucination)을 결정적 테스트로 포착 | 테스트 작성에 인간의 도메인 지식 필요 |
| 버그 40~80% 감소 (2025 DORA 보고서) | 레거시 모노리스 리팩토링 비용 |
| 코드 품질에 대한 신뢰 확보 가능 | 단위 테스트 외의 통합/기능 테스트는 AI에 부적합 |
| AI의 전달 속도를 오히려 향상 | 학습 곡선: 기존 "테스트 후 작성" 습관 변경 필요 |

### 적용 사례 및 도구

- **Claude Code SKILL.md**: TDD 루프를 SKILL.md 파일로 인코딩하여 에이전트가 한 번에 하나의 테스트-구현 사이클을 따르도록 강제
- **Jest/Vitest, pytest**: AI 에이전트의 빠른 피드백 루프에 이상적인 단위 테스트 프레임워크
- **CI/CD 통합**: AI가 생성한 코드가 CI 파이프라인을 통과해야만 머지 허용

### 주요 제안자/옹호자

- **Kent Beck**: TDD 원조 창시자 (Extreme Programming Explained), AI 시대에도 TDD의 유효성 강조
- **Simon Willison**: "테스트-우선 개발은 코딩 에이전트에 환상적으로 적합하다"
- **Andre Darcie**: "AI 에이전트 세계에서 TDD는 선택적 좋은 관행에서 사실상 필수가 되었다"

## 3. SDD -- 스펙 주도 개발

### 정의

Spec-Driven Development(SDD)는 **구조화되고 기계 판독 가능한 명세(specification)를 개발 라이프사이클의 중심**에 놓는 패러다임이다. 코드가 아닌 스펙을 주요 산출물(primary artifact)로 취급하며, 코드는 스펙에서 파생되는 "마지막 1마일(last-mile)" 출력이 된다.

### 등장 배경

Vibe Coding이 빠르게 확산된 후, 그 한계가 뚜렷해졌다:
- AI 에이전트가 API를 환각하고, 라이브러리 버전을 혼합하고, 의도하지 않은 부작용을 도입
- 개발자가 정확한 의도를 표현하기 어려움
- AI에게 아키텍처 결정이나 제약의 지속적 기억이 없음

SDD는 이에 대한 **업계의 궤도 수정(course correction)** 으로 등장했다.

### 핵심 원칙

1. **스펙이 소스 오브 트루스(Source of Truth)**: 코드가 아닌 스펙이 시스템의 진실의 원천
2. **실행 가능한 스펙(Executable Specs)**: 스펙이 단순 문서가 아닌, AI가 직접 실행할 수 있는 형태
3. **점진적 정제(Iterative Refinement)**: 스펙을 반복적으로 정제하며 AI 출력을 개선
4. **검증 게이트(Verification Gates)**: 각 단계에서 스펙 준수 여부를 검증

### 주요 SDD 프레임워크

| 프레임워크 | 특징 | 적합한 경우 |
|------------|------|-------------|
| **GitHub Spec-Kit** | Slash 커맨드 기반 (`/plan`, `/execute`, `/test`), Constitution.md | GitHub 생태계 사용 팀 |
| **Amazon Kiro** | AWS 통합, 클라우드 네이티브 스펙 | AWS 기반 프로젝트 |
| **BMAD Method** | 다중 에이전트 오케스트레이션, 역할 기반 워크플로우 | 복잡한 팀 프로젝트 |
| **OpenSpec** | 오픈소스, 커뮤니티 기반 | 벤더 종속 회피 |
| **Tessl** | Context Engineering 중심, CDLC 개념 | 대규모 조직 |
| **No Framework** | CLAUDE.md / .cursorrules 기반 직접 구성 | 소규모 / 개인 프로젝트 |

### SDD 워크플로우

```
1. [인간] 요구사항을 구조화된 스펙(Markdown/YAML/JSON)으로 작성
2. [인간] 아키텍처 결정, 제약조건, 기술 스택 명시
3. [AI 에이전트] 스펙을 읽고 구현 계획 제안
4. [인간] 계획 검토 및 승인
5. [AI 에이전트] 스펙에 따라 코드 생성
6. [자동화] 스펙 준수 여부 검증 (테스트, 린팅 등)
7. 반복
```

### 스펙의 구성 요소 예시

```markdown
# Feature: User Authentication
## Requirements
- OAuth 2.0 via Google, GitHub
- JWT with 24-hour expiry
- Rate limiting: 5 failed attempts -> 15-minute lockout

## Constraints
- Must use existing PostgreSQL database
- Response time < 200ms at p99
- No new npm dependencies without approval

## Acceptance Criteria
- [ ] User can sign in with Google OAuth
- [ ] Invalid tokens return 401
- [ ] Rate limiting triggers after 5 failures
```

### 장단점

| 장점 | 단점 |
|------|------|
| AI에게 명확한 지침 제공, 환각 감소 | 초기 스펙 작성에 상당한 노력 필요 |
| 유지보수성 높음 (스펙이 문서 역할) | 과도한 사전 계획으로 탐색적 개발 저해 가능 |
| 팀 간 일관성 확보 | 스펙의 부패(staleness) 관리 필요 |
| 검증 가능한 산출물 | 빠른 프로토타이핑에 부적합 |
| AI 에이전트의 자율성과 정확성의 균형 | 프레임워크별 학습 비용 |

### 주요 제안자/옹호자

- **Augment Code**: SDD 가이드 및 도구 제공, "Spec + TDD" 조합 제안
- **Nagaprasad Sathyanarayana**: "스펙을 문서에서 실행 가능한 진실(Executable Truth)로" 개념 제시
- **Alex Rezvov**: Specification-Driven Development의 네 가지 기둥 정의
- **Amazon (Kiro)**: 클라우드 네이티브 SDD 도구 출시

## 4. PDD -- 프롬프트 주도 개발

### 정의

Prompt-Driven Development(PDD)는 **프롬프트를 검증 가능한 명세(verifiable specification)로 취급**하는 개발 방법론이다. 위시리스트나 채팅이 아닌, 현실에 대해 측정되어야 하는 계약(contract)으로 프롬프트를 다룬다.

### PDD의 매니페스토

PDD의 핵심 선언(DEV Community의 blame76이 작성한 매니페스토에 기반):

**PDD가 아닌 것:**
- 버즈워드 피치용 워크플로우가 아니다
- "테스트 생성하고 기도하기"가 아니다
- "LLM이 내 코드를 작성한다" (책임 없는 위임)가 아니다
- "프롬프트 엔지니어링" (더 많은 단어 = 더 나은 마법)이 아니다

**PDD인 것:**
- "완료(done)"를 정의할 수 있을 때만 코드 작성
- 프롬프트가 측정 가능해질 때까지 반복
- 테스트는 심판(referee)이지 장식이 아니다
- 명세로서의 프롬프트(specification-first)

### 핵심 원칙

1. **프롬프트는 명세다**: 프롬프트를 충동적 요청이 아닌, 검증 가능한 계약으로 작성
2. **측정 가능성**: 시스템을 측정할 수 없으면 제어할 수 없다
3. **역순 워크플로우**: `프롬프트(명세) -> 테스트(현실 센서) -> 프롬프트(반복: 시에서 정밀함으로) -> 코드(테스트 우리 안의 구현)`
4. **의도의 명시적 표현**: 개발자의 의도를 자연어로 명확히 표현하고, 이를 코드 생성의 입력으로 사용

### PDD 워크플로우 (The Loop)

```
전통적 (안타깝게도 일반적인) 방식:
  프롬프트 -> 코드 -> 수정 -> 더 수정 -> "왜 이렇게 오래 걸리지?"

PDD 방식:
  1. 프롬프트 (명세로서)
  2. 테스트 (현실 센서로서)
  3. 프롬프트 반복 (시에서 정밀함으로)
  4. 코드 (테스트 우리 안의 구현)
```

### PDD의 실제 적용

**좋은 PDD 프롬프트 예시:**
```
"사용자 인증 시스템을 구현하라.
- 입력: email(string, RFC 5322), password(string, 최소 8자, 대소문자+숫자+특수문자)
- 출력: JWT 토큰(24시간 만료) 또는 에러 코드(401/429)
- 제약: 실패 5회 시 15분 잠금, 응답 시간 p99 < 200ms
- 테스트 가능한 동작: 유효한 자격증명 -> 토큰 반환, 잠긴 계정 -> 429 반환"
```

**나쁜 PDD 프롬프트 예시:**
```
"로그인 기능 만들어줘"
```

### 장단점

| 장점 | 단점 |
|------|------|
| 자연어로 의도를 표현하므로 접근성 높음 | 좋은 프롬프트 작성 능력 필요 (새로운 스킬셋) |
| 프롬프트 자체가 문서 역할 | LLM의 "공손한 거짓말"에 취약 (모순을 지적하지 않음) |
| 반복적 정제로 점진적 개선 가능 | 프롬프트 품질이 출력 품질을 결정 |
| TDD와 자연스럽게 결합 가능 | 복잡한 시스템에서 프롬프트만으로 충분한 명세 어려움 |
| 비개발자도 참여 가능 | 프롬프트의 버전 관리/재사용 체계 미성숙 |

### 주요 제안자/옹호자

- **blame76**: PDD 매니페스토 작성자 ("A Manifesto Against Comfortable Guessing")
- **Haim Michael**: "From Intent to Execution" 개념 제시
- **Maddy**: 시니어 엔지니어/프로덕트 리더를 위한 PDD 플레이북 작성
- **Samuel (LinkedIn)**: "The Next Frontier in AI-Enhanced Software Engineering"

## 5. ADD -- 에이전트 주도 개발

### 정의

Agent-Driven Development(ADD)는 **AI 에이전트와 인간 개발자가 잘 정의된 프로세스를 통해 협업하는 구조화된 방법론**이다. 에이전트가 구현, 문서화, 테스팅, 버저닝의 "그런트 워크(grunt work)"를 처리하고, 인간(Editor)이 방향, 도메인 전문성, 비판적 사고를 제공한다.

### 핵심 개념

> "ADD는 Vibe Coding이 성숙했을 때 되고 싶은 것이다." -- Remo H. Jansen

ADD와 Vibe Coding의 결정적 차이:
- Vibe Coding은 **자발적, 혼란적, 확장 불가능**
- ADD는 **구조적, 엄격하고, 엔터프라이즈급 시스템을 위해 설계됨**

### 핵심 원칙

1. **신뢰는 전제조건이 아니라 프로세스의 산물**: "AI를 신뢰할 수 없다"가 아니라, 프로세스를 통해 신뢰를 획득
2. **엄격한 감독(Strict Supervision)**: 에이전트 출력에 대한 체계적 감독
3. **자동화된 테스팅 및 CI/CD**: 기존 DevOps 관행이 에이전트의 안전망 역할
4. **철저한 계획과 문서화**: 사전 계획, 마일스톤 정의
5. **점진적 개발과 시맨틱 버저닝**: 증분적 개발, 변경 추적
6. **모듈러 아키텍처**: 에이전트는 잘 정의된 경계에서 번성

### Editor의 역할

ADD에서 인간 개발자는 **프로덕트 아키텍트이자 품질 게이트키퍼**가 된다. 모든 줄의 코드를 작성하는 것이 아니라:
- 시스템을 설계하고
- 마일스톤을 정의하고
- 에이전트의 작업을 검토한다

> "어떻게 구현할까?"에서 "에이전트가 올바르게 구현하도록 어떻게 안내할까?"로의 마인드셋 전환

### ADD 워크플로우

```
1. [Editor] 시스템 설계, 아키텍처 결정, 마일스톤 정의
2. [Editor] 기능 명세 및 수용 기준 작성
3. [AI Agent] 구현 계획 제안
4. [Editor] 계획 검토 및 승인
5. [AI Agent] 코드 구현 + 테스트 작성 + 문서 생성
6. [자동화] CI/CD 파이프라인 검증
7. [Editor] 최종 코드 리뷰, 보안 감사
8. [자동화] 배포
9. 반복 (시맨틱 버저닝)
```

### 에이전틱 개발의 실제 도구

| 도구 | 역할 |
|------|------|
| Claude Code (Agent Mode) | 레포지토리 전체 접근, 파일 읽기/쓰기, 스크립트 실행 |
| Cursor (Composer) | 다중 파일 편집, 코드베이스 인식 |
| GitHub Copilot (Agent Mode) | 레포 구조 기반 에이전트 워크플로우 |
| Windsurf (Cascade) | 자율적 다단계 작업 실행 |

### 에이전트가 할 수 있는 것 vs 인간이 소유하는 것

**에이전트 영역:**
- 코드 검색, 읽기, 작성
- 셸 명령 실행 (빌드, 테스트, 배포)
- 패키지 설치, 의존성 관리
- git 명령 실행
- 문서 생성

**인간 영역:**
- 전략적 의사결정 (무엇을 만들지)
- 아키텍처 선택 (에이전트가 옵션을 제안할 때)
- 보안 검증 (특히 사용자 입력, 인증, 데이터 처리)
- 최종 품질 검증

### 장단점

| 장점 | 단점 |
|------|------|
| 기능 개발 속도 극적 향상 (10x) | 강력한 DevOps 인프라 전제 |
| 일관된 코드 스타일 (지침 파일이 표준 인코딩) | 레거시 시스템에 적용 어려움 |
| 코드와 함께 문서 자동 생성 | 에이전트의 아키텍처 실수 가능 |
| 반복 작업에서 해방 | 복잡한 디버깅은 여전히 인간 필요 |
| 체계적 아키텍처 (레포 구조가 패턴 강제) | 보안은 맹목적으로 신뢰할 수 없음 |

### 주요 제안자/옹호자

- **Remo H. Jansen**: ADD 개념 정립, DEV Community에서 체계적 방법론 제시 (2025.07)
- **Joshua Ayson**: 에이전틱 개발의 실전 가이드 (6개월 실무 경험 기반)
- **Todd Orr**: AI 에이전트로 소프트웨어 구축하는 전문적 워크플로우 제시
- **Eranga Bandara et al.**: Agentsway 논문 -- AI 에이전트 기반 팀의 소프트웨어 개발 방법론 (arXiv, 2025.10)

## 6. VDD -- 바이브 코딩(Vibe Coding)

### 정의

바이브 코딩(Vibe Coding)은 **자연어로 원하는 것을 설명하고 AI가 모든 코드를 작성하게 하는 AI 보조 개발 방식**이다. 구문을 학습하거나, 에러를 디버깅하거나, 인프라를 관리하는 대신, 원하는 것의 "느낌(vibe)"과 기능을 설명하면 AI가 구현을 처리한다.

### 기원

2025년 2월 3일(일부 기록에서는 2월 6일), Andrej Karpathy가 X(구 트위터)에 다음과 같이 게시했다:

> "There's a new kind of coding I call 'vibe coding', where you fully give in to the vibes, embrace exponentials, and forget that the code even exists."

Karpathy는 다음과 같이 설명했다:
- Cursor Composer에 SuperWhisper 음성 입력으로 대화
- "사이드바 패딩을 반으로 줄여줘" 같은 요청 (CSS를 직접 찾기 귀찮아서)
- 모든 변경에 "Accept All" 클릭
- 에러 메시지를 설명 없이 그대로 채팅에 복사-붙여넣기
- 코드가 자신의 이해를 넘어서 성장했고, AI가 버그를 못 고치면 사라질 때까지 무작위 변경 요청

그의 말: 이것은 **주말 프로젝트용**이지 프로덕션 소프트웨어용이 아니다.

### Karpathy의 기여 -- 정확한 평가

**Karpathy가 한 것:**
1. **명명(Naming)**: 기억하기 쉽고, 공유 가능하고, 즉시 묘사적인 용어 부여
2. **정당화(Legitimation)**: AI 커뮤니티에서 존경받는 인물의 공개적 사용이 다른 개발자에게 "허락" 부여
3. **어휘(Vocabulary)**: 기사, 컨퍼런스, 대화에서 사용할 공통 어휘 생성
4. **주류 계기(Mainstream Moment)**: 2025년 2월이 바이브 코딩이 주류 기술 담론의 주제가 된 시점

**Karpathy가 하지 않은 것:**
- Co-Creator 모델을 창시하지 않았다 (그것은 Dany Kitishian의 기여)
- Post-Syntax 테제를 확립하지 않았다
- 학술 커리큘럼을 구축하지 않았다

> 참고: 2023년 1월 24일 Karpathy는 "The hottest new programming language is English"라고 게시한 바 있다. 이는 바이브 코딩의 개념적 영역이 방법론이 공식화되기 전에도 인식되고 있었음을 보여준다.

### 문화적 영향

- Collins Dictionary **2025 올해의 단어** 선정
- 검색량 6,700% 급증 (2025년 봄)
- r/vibecoding 서브레딧 87,000+ 구독자
- Y Combinator 2025 겨울 배치 25%+ 가 거의 전적으로 AI 생성 코드베이스
- **Linus Torvalds** (Linux/Git 창시자): AudioNoise 취미 프로젝트에서 Python 도구를 바이브 코딩으로 작성, 하지만 C 핵심 컴포넌트는 직접 코딩. "시작하는 데는 괜찮지만 유지보수에는 끔찍한 아이디어"

### 바이브 코딩 워크플로우

```
1. 원하는 것을 자연어로 설명
   "랜딩 페이지에 히어로 섹션, 이메일 가입 폼, 3단계 가격표 만들어줘"
2. AI가 코드 생성 (HTML, CSS, JS, React, API 등)
3. 결과를 확인 -- 작동하는가? 보기 좋은가?
   (diff를 줄별로 읽지 않음. 요청한 대로인지 확인)
4. 반복 -- "블러가 너무 심해, 줄여줘" / "모바일 버전 추가해"
5. 에러 발생 시, 에러 메시지를 AI에 복사-붙여넣기
```

### 주요 도구

**AI 네이티브 IDE (개발자용):**
| 도구 | 특징 |
|------|------|
| Cursor | Composer 기능, 다중 파일 편집, 코드베이스 인식 |
| Claude Code | 터미널 기반 에이전트, 앱 빌딩 벤치마크 93% 성공률 |
| Windsurf | Cascade 자율 에이전트 (OpenAI에 인수됨) |

**브라우저 기반 빌더 (모든 사람용):**
| 도구 | 특징 |
|------|------|
| Bolt.new | 프롬프트 -> 라이브 URL, 빠른 프로토타이핑 |
| Lovable | 디자인 우선, 세련된 UI, Supabase 통합 |
| Replit | 전체 개발 환경, 즉시 배포 |

### 현실적 문제점

1. **디버깅 벽**: 코드를 수락만 하다 보면 무엇이 어디에 있는지, 어떻게 연결되는지 모르게 됨
2. **3개월 블랙박스**: 바이브 코딩으로 만들고 3개월 후 아무도 작동 방식을 설명 못 함 ("바이브 코딩 숙취")
3. **보안 취약점**: AI 생성 코드의 약 45%에 보안 결함. Lovable 앱 1,645개 중 170개에서 개인정보 노출 취약점 발견 (2025.05)
4. **Slopsquatting**: AI가 자주 환각하는 패키지 이름으로 악성 패키지 등록하는 공격
5. **METR 패러독스**: 16명의 경험 많은 개발자 연구에서 AI 도구가 복잡한 작업에서 19% 느려졌지만, 80%가 "더 쉽고 즐겁다"며 계속 사용
6. **기술 부채**: AI 생성 코드는 즉각적 문제는 해결하지만 모듈성, 쿼리 최적화, 확장성을 무시하는 경향

### 바이브 코딩이 적합한 경우 vs 부적합한 경우

**적합:**
- 프로토타이핑 / MVP 구축
- 주말 사이드 프로젝트, 내부 도구
- 속도가 장기 유지보수보다 중요할 때
- 아키텍처 커밋 전 아이디어 탐색

**부적합:**
- 사용자 데이터를 다루는 프로덕션 시스템
- 보안/컴플라이언스가 중요한 분야 (헬스케어, 금융)
- 팀이 수년간 유지보수해야 하는 프로젝트
- 예측 가능한 대규모 성능 필요

### 장단점

| 장점 | 단점 |
|------|------|
| 극적인 개발 속도 (주 -> 시간) | 보안 취약점 (~45% AI 코드에 결함) |
| 비개발자도 소프트웨어 구축 가능 | 유지보수 불가능한 블랙박스 생성 위험 |
| 아이디어 -> 작동하는 앱의 진입 장벽 최소화 | 기술 부채 급속 축적 |
| 창의적 탐색에 이상적 | 프로덕션 환경에 부적합 |
| Collins 올해의 단어 2025 -- 문화적 영향력 | 경험 많은 개발자 + 바이브코딩 = 강력, 초보자 + 바이브코딩 = 실패 |

## 7. 기타 AI 시대 개발 방법론

### 7.1 BMAD Method (Breakthrough Method for Agile AI-Driven Development)

**정의:** AI 코딩 어시스턴트를 건망증 있는 채팅 파트너에서 **명확한 핸드오프, 버전 관리된 워크플로우, 제도적 기억을 가진 전문 에이전트 팀**으로 전환하는 프레임워크.

**핵심 개념 -- "Methodology as Code":**
- 전략, 도메인 전문성, 품질 게이트가 모두 버전 관리된 파일에 존재
- GitHub 37k+ 스타, 117명 기여자, v6.0.3 (2026.02 기준)
- `npx bmad-method install` CLI로 설치

**핵심 아키텍처:**
- **에이전트(Agents)**: 전문화된 AI 역할 (PM, 아키텍트, 개발자, 테스터 등)
- **워크플로우(Workflows)**: 50+ 정의된 워크플로우
- **작업(Tasks)**: 단위 작업 정의
- **템플릿(Templates)**: 산출물 형식 표준화
- **모듈(Modules)**: 재사용 가능한 기능 블록

**4단계 개발 페이즈:**
1. **Analysis**: 문제 정의, 사용자, MVP 범위
2. **Planning**: 요구사항, 페르소나, 성공 지표
3. **Solutioning**: 아키텍처 설계, 기술 선택
4. **Implementation**: 코드 구현, 테스팅, 배포

**3가지 트랙:**
- Quick Flow: 소규모 프로젝트
- BMad Method: 중간 규모
- Enterprise: 대규모 조직

**장점:** 팀 일관성, 지식 누적(compound), 제품-엔지니어링 공통 언어
**단점:** 21개 에이전트와 50+ 워크플로우는 소규모 프로젝트에 과도

**참고:** [BMAD Method GitHub](https://github.com/bmad-method) | [Signal from Noise 리뷰](https://www.signalfromnoise.co.uk/articles/bmad-method)

### 7.2 ICDD (Iterative Context-Driven Development)

**정의:** **인간 중심, 도구 비의존적(tool-agnostic) 방법론**으로, 인간의 탐색적 사고와 AI의 컨텍스트 기반 작업을 연결하는 다리 역할을 하는 경량 프레임워크.

**철학 -- Kasparov의 법칙:**
> "약한 인간 + 기계 + 더 나은 프로세스가 강한 인간 + 기계 + 열등한 프로세스를 이긴다."

**3대 핵심 원칙:**
1. **Radical Simplicity (급진적 단순함)**: 프로세스가 해결하는 문제보다 단순해야 한다. Markdown 파일과 자연어만 필요
2. **Intuitive Exploration (직관적 탐색)**: 계획은 살아 있는 지도. 코딩하면서 계획을 함께 발전시킴
3. **Absolute Agnosticism (절대적 불가지론)**: 회사를 바꾸거나 노트북을 바꿔도 프로세스가 깨지지 않아야 함. IDE, AI 에이전트, 워크플로우 도구에 종속되지 않음

**디렉토리 구조:**
```
project/
├── .context/                    # "공유 두뇌"
│   ├── system_context.md        # 글로벌 진실 (프로젝트 "헌법")
│   ├── backlog.md               # 동적 백로그
│   ├── active/                  # 현재 진행 중 기능
│   │   └── PROJ-101-user-auth.md
│   ├── archive/                 # 완료된 기능
│   └── adr/                     # 아키텍처 결정 기록
│       └── PROJ-101-db-choice.md
```

**6가지 페르소나 에이전트:**
1. Planner & Architect -- 시스템 컨텍스트 수호자
2. Codex (Engineer) -- 빌더
3. Test Engineer -- 회의론자
4. Code Reviewer -- 비평가
5. Security Engineer -- 편집증적 보호자
6. Technical Writer -- 역사가

**Golden Rule:** 컨텍스트 파일 없이 코딩을 시작하지 않는다.

**참고:** [ICDD 가이드](https://blog.softwaresalt.com/posts/icdd/) -- Derek Williams, CC BY 4.0

### 7.3 Context Engineering / CDLC (Context Development Lifecycle)

**정의:** **컨텍스트(맥락)를 코드와 동등한 엔지니어링 아티팩트로 취급**하는 접근법. 생성, 평가, 배포, 관찰의 라이프사이클을 통해 AI에게 제공하는 컨텍스트를 지속적으로 개선한다.

**제안자:** Patrick Debois -- **DevOps의 아버지**로 알려진 인물이 DevOps 다음의 패러다임으로 CDLC를 제시 (Tessl, 2026.02)

**핵심 인사이트:**
> "코딩 에이전트가 코드를 작성하고 있다. 병목은 더 이상 얼마나 빨리 코드를 작성하고 배포하는가가 아니다. 코드가 무엇을 해야 하는지, 왜 해야 하는지, 시스템의 복잡한 현실에서 어떻게 행동해야 하는지를 얼마나 잘 설명할 수 있는가가 병목이다."

**CDLC의 4단계:**

| 단계 | 설명 |
|------|------|
| **Generate (생성)** | 암묵적 조직 지식을 명시적으로. 기술, 프로젝트, 비즈니스 컨텍스트 포함 |
| **Evaluate (평가)** | 컨텍스트의 TDD -- 시나리오 정의, AI 출력이 의도에 맞는지 평가 |
| **Distribute (배포)** | 컨텍스트를 패키지처럼 버전 관리, 배포, 보안 관리 (npm/pip처럼) |
| **Observe (관찰)** | 실제 사용에서 학습 -- 에이전트의 질문, 예상치 못한 선택, 의도 불일치 관찰 |

**DevOps와의 유사성:**
- DevOps가 개발과 운영 사이의 피드백 루프를 인식한 것처럼, CDLC는 컨텍스트 생성과 컨텍스트 운용이 분리할 수 없음을 인식
- 차이점: DevOps는 팀 간 협업 인센티브 정렬이 어려웠지만, 컨텍스트에서는 **이기적 동기(selfish reason)** 가 자연스럽게 정렬 -- 더 나은 컨텍스트 = 더 나은 에이전트 출력

**"무한 컨텍스트 윈도우가 해결해주지 않는다":**
> 윈도우 크기가 커져도, 도전은 "무엇을 포함할지"에서 "어떻게 일관되고, 최신이고, 신뢰할 수 있게 유지할지"로 바뀐다. 큐레이션에서 거버넌스로. 이것은 더 어려울 수 있다.

**참고:**
- [The Context Development Lifecycle](https://tessl.io/blog/context-development-lifecycle-better-context-for-ai-coding-agents) -- Patrick Debois, Tessl
- [2025: The Year Context Became King](https://www.forrester.com/blogs/2025-the-year-context-became-king-and-how-developers-are-wielding-it/) -- Forrester

### 7.4 DDD (Document-Driven Development)

**정의:** 코드 작성 전에 **문서를 먼저 작성**하고, 그 문서를 AI의 컨텍스트 및 검증 기준으로 사용하는 접근법. SDD와 유사하지만 더 넓은 범위의 문서(README, ADR, API 문서 등)를 포함한다.

**AI 시대에서의 의미:**
- 문서가 AI 에이전트의 "지침 파일(instruction files)"로 작동
- CLAUDE.md, .cursorrules, copilot-instructions.md 등이 DDD의 실제 구현
- 에이전트가 레포를 탐색하고 이해하고 확장할 수 있도록 하는 구조적 기반

**문서의 계층:**
1. **시스템 수준**: README.md, ARCHITECTURE.md, 기술 스택 정의
2. **디렉토리 수준**: 각 주요 폴더의 README.md
3. **파일 수준**: 파일 상단의 목적/사용법 주석
4. **에이전트 지침**: .github/copilot-instructions.md, CLAUDE.md

### 7.5 기타 주목할 만한 접근법

**Ralph Loop / Self-Referential Loop:**
- 작업 완료까지 자기 참조적 루프를 실행하는 방식
- 검증 리뷰어를 통한 확인 후 완료
- oh-my-claudecode 등에서 구현

**Chimera Coding:**
- 바이브 코딩과 전통적 코딩의 하이브리드
- 핵심 로직은 인간이 직접, 주변 도구/UI는 바이브 코딩
- Linus Torvalds의 실제 사용 패턴과 일치

**TDAID (Test-Driven AI Development):**
- TDD와 AI를 결합한 특화 변형
- AI 에이전트 자체의 동작을 테스트하는 데 초점

## 9. 전통적 개발 방법론과의 비교

### 9.1 패러다임 전환

| 관점 | 전통적 방법론 | AI 시대 방법론 |
|------|-------------|---------------|
| **코드 작성 주체** | 인간 | AI (인간 감독 하) |
| **핵심 기술** | 프로그래밍 언어 숙련 | 의도 표현, 컨텍스트 엔지니어링 |
| **설계 문서** | 커뮤니케이션 도구 | AI에 대한 실행 가능한 지침 |
| **테스트** | 품질 보증 도구 | AI 제어 메커니즘 (우리/cage) |
| **코드 리뷰** | 버그 발견 + 지식 공유 | AI 출력 검증 + 전략적 의사결정 |
| **개발 속도** | 주~월 단위 | 시간~일 단위 |
| **병목** | 코드 작성 속도 | 의도 명세 + 컨텍스트 품질 |

### 9.2 전통 방법론의 AI 시대 진화

| 전통 방법론 | AI 시대 대응/진화 |
|------------|-----------------|
| **Waterfall** | SDD (구조화된 사전 계획, 하지만 반복적) |
| **Agile/Scrum** | ADD (스프린트 + 에이전트 협업) |
| **XP (Extreme Programming)** | TDD + AI (TDD, 페어 프로그래밍 -> 인간+AI 페어링) |
| **Lean** | Vibe Coding (최소 실행 가능 제품 빠른 검증) |
| **DevOps** | Context Engineering / CDLC (컨텍스트의 CI/CD) |
| **DDD (Domain-Driven Design)** | SDD + Context Engineering (도메인 지식을 AI 컨텍스트로) |

### 9.3 변하지 않는 것들

AI 시대에도 여전히 유효한 원칙들:

1. **관심사의 분리 (Separation of Concerns)**: 모듈러 아키텍처가 AI 에이전트에게도 필수
2. **SOLID 원칙**: 깨끗한 코드 구조가 AI 출력 품질을 결정
3. **테스팅의 가치**: TDD가 "선택에서 필수"로 격상
4. **문서화의 가치**: 인간을 위한 문서에서 "AI를 위한 실행 가능한 명세"로 진화
5. **코드 리뷰**: "모든 줄 읽기"에서 "전략적 검증"으로 역할 변화
6. **보안 의식**: AI가 생성한 코드에 대한 보안 감사의 중요성 증가

## 10. 결론 및 실무 적용 가이드

### 10.1 핵심 통찰

1. **하나의 방법론이 모든 것을 해결하지 않는다**: 프로젝트의 규모, 팀 구성, 위험 수준에 따라 적절한 조합 선택
2. **스펙트럼 위에 있다**: Vibe Coding(탐색적) <-> BMAD(구조적) 스펙트럼에서 프로젝트에 맞는 지점 선택
3. **Spec + TDD 조합이 가장 강력**: Augment Code 등 여러 출처에서 "스펙 기반 지침 + 테스트 기반 검증"의 조합을 가장 효과적이라 평가
4. **컨텍스트가 왕이다**: Patrick Debois의 CDLC 개념처럼, 모델 성능보다 컨텍스트 품질이 결과를 결정
5. **인간의 역할은 사라지지 않고 진화한다**: 코드 작성자에서 아키텍트/감독자/전략가로

### 10.3 미래 전망

AI 시대의 개발 방법론은 아직 초기 단계에 있다. 2025-2026년의 빠른 진화를 기반으로 예측되는 향후 방향:

- **에이전트 전문화**: 프론트엔드, 백엔드, 인프라 에이전트가 인간 에디터의 지도 하에 협업
- **컨텍스트의 상품화**: 컨텍스트 패키지가 npm 패키지처럼 공유/배포
- **하이브리드 접근법 표준화**: 순수 방법론보다 Chimera Coding 같은 혼합 접근법이 주류화
- **AI 리터러시 필수화**: "프롬프트 작성", "컨텍스트 엔지니어링"이 핵심 개발자 역량으로 자리잡음
- **도구 수렴**: 개별 방법론 도구들이 통합 플랫폼으로 수렴

> **핵심 메시지:** AI 시대에 승리하는 팀은 최고의 모델을 가진 팀이 아니다. 최고의 컨텍스트를 가진 팀이다 -- 생성되고, 평가되고, 배포되고, 지속적으로 개선되는 컨텍스트.
