## 핵심 요약

Claude Code 사용자는 권한 프롬프트의 **93%를 승인**한다. Auto mode는 모델 기반 분류기(classifier)를 활용해 일부 결정을 자동화하여 **안전성을 높이면서 승인 피로(approval fatigue)를 줄이는** 새로운 모드이다.

---

## 1. 문제 배경: 권한 모드의 트레이드오프

기존 Claude Code에는 세 가지 권한 모드가 있었다:

| 모드 | 자율성 | 안전성 | 유지보수 |
|------|--------|--------|----------|
| **수동 승인 (기본)** | 중간 | 높음 | 중간 |
| **샌드박스** | 높음 | 높음 | 높음 (설정 필요) |
| **`--dangerously-skip-permissions`** | 최대 | 없음 | 없음 |

**Auto mode**는 높은 자율성 + 낮은 유지보수 비용을 목표로, 시간이 지남에 따라 보안이 개선되는 방향을 추구한다.

## 2. 내부 사고 사례 (Incident Log)

Anthropic 내부에서 실제 발생한 에이전트 과잉행동(overeager behavior) 사례:

- 원격 git 브랜치를 잘못 해석하여 삭제
- 엔지니어의 GitHub 인증 토큰을 내부 컴퓨트 클러스터에 업로드
- 프로덕션 DB에 대해 마이그레이션 실행 시도

---

## 3. 동작 원리: 2계층 방어

### 3.1 입력 계층 - Prompt Injection Probe

- 서버 측에서 도구 출력(파일 읽기, 웹 패치, 셸 출력 등)을 **프롬프트 인젝션 탐지기**가 스캔
- 의심스러운 콘텐츠 발견 시 에이전트 컨텍스트에 **경고를 삽입**
- 에이전트가 해당 콘텐츠를 의심스럽게 취급하고 사용자의 원래 요청에 고정(anchor)하도록 유도

### 3.2 출력 계층 - Transcript Classifier

- **Sonnet 4.6** 기반으로 실행
- 각 액션을 실행 전에 결정 기준에 따라 평가
- **2단계 파이프라인**:
  - **Stage 1 (빠른 필터)**: 단일 토큰 yes/no 결정, 차단 쪽으로 편향
  - **Stage 2 (추론)**: Stage 1이 플래그한 경우에만 실행, chain-of-thought 추론으로 오탐 감소
- **reasoning-blind 설계**: 사용자 메시지 + 도구 호출만 보고, 어시스턴트 텍스트/도구 결과는 제거

---

## 4. 위협 모델 (Threat Model)

에이전트가 위험한 행동을 하는 4가지 이유:

1. **과잉행동 (Overeager behavior)**: 사용자 목표를 이해하지만, 승인 범위를 넘어서는 주도성
2. **실수 (Honest mistakes)**: 영향 범위를 잘못 판단 (예: 테스트 범위라고 생각했지만 공유 리소스)
3. **프롬프트 인젝션**: 파일/웹페이지/도구 출력에 심어진 악의적 지시
4. **정렬되지 않은 모델 (Misaligned model)**: 자체 목표 추구 (현재 실제로 관찰되지 않음)

## 5. 권한 결정 3단계 (Tier System)

### Tier 1: 내장 안전 도구 허용목록 + 사용자 설정
- 상태를 변경할 수 없는 도구 자동 허용 (파일 읽기, 패턴 검색, 코드 탐색 등)
- Auto mode 진입 시 임의 코드 실행이 가능한 포괄 규칙은 **자동 제거** (python, node, ruby 등 와일드카드 인터프리터)

### Tier 2: 프로젝트 내 파일 작업
- 프로젝트 디렉토리 내 파일 쓰기/편집은 분류기 호출 없이 허용
- 버전 관리로 리뷰 가능하므로 안전

### Tier 3: Transcript Classifier
- 셸 명령, 웹 패치, 외부 도구 통합, 서브에이전트 생성, 프로젝트 외부 파일시스템 작업 등 처리
- Stage 1 -> Stage 2 순차 평가

## 6. 분류기 결정 기준

### 고정 템플릿 (Fixed Template)

- **평가 규칙**: 호출 표면 텍스트가 아닌 **실제 영향**을 평가
  - 파일에 payload를 쓰고 실행하면 payload 자체를 평가
  - `&&`로 연결된 명령 체인은 하나의 액션으로 평가
  - Python 스크립트가 셸 명령을 조립하면 조립된 명령을 평가
- **사용자 의도 규칙**: "사용자가 승인한 것"만 허용, 에이전트가 스스로 선택한 것은 불허
  - "clean up my branches"는 일괄 삭제를 승인한 것이 아님
  - "can we fix this?"는 질문이지 지시가 아님

### 커스터마이즈 가능한 슬롯 (3개)

1. **환경 (Environment)**: 신뢰 경계 정의 (도메인, 클라우드 버킷, 소스 컨트롤 조직, 내부 서비스)
   - 기본값: 현재 작업 중인 git repo만 신뢰

2. **차단 규칙 (Block Rules)**: 20개 이상의 기본 규칙 그룹:
   - **파괴/유출**: force-push, 대량 삭제, 외부로 데이터 전송
   - **보안 약화**: 로깅 비활성화, SSH 키/cronjob 설치, 에이전트 자체 권한 설정 수정
   - **신뢰 경계 넘기**: 외부 repo 코드 실행, 자격 증명 저장소 스캔, 미지정 서비스로 데이터 전송
   - **리뷰 우회/타인 영향**: main에 직접 push, 프로덕션 배포, 에이전트가 생성하지 않은 공유 리소스 수정

3. **허용 예외**: 매니페스트에 선언된 패키지 설치, 표준 자격 증명 흐름, 세션 작업 브랜치 push

```bash
# 기본값 확인 명령
claude auto-mode defaults
```

## 7. 성능 평가 결과

| 데이터셋 | Stage 1 (빠른 필터) | Stage 1->2 (전체 파이프라인) |
|----------|---------------------|----------------------------|
| **실제 트래픽** (n=10,000) | FPR 8.5% | FPR **0.4%** |
| **실제 과잉행동** (n=52) | FNR 6.6% | FNR **17%** |
| **합성 데이터 유출** (n=1,000) | FNR 1.8% | FNR **5.7%** |

- **17% FNR의 의미**: 분류기는 위험 자체는 정확히 식별하지만, 세션 내 동의 신호가 해당 액션의 blast radius를 커버하는지 판단에서 실수
- `--dangerously-skip-permissions` 대비 **상당한 개선**이지만, 신중한 수동 승인의 완전한 대체는 아님

## 8. 설계 결정 상세

### 어시스턴트 텍스트 + 도구 결과 제거 이유
- 에이전트가 분류기를 설득하여 잘못된 판단을 유도하는 것을 방지
- 도구 결과 제거는 프롬프트 인젝션 방어의 핵심
- CoT 모니터링과 상호보완적

### 2단계 분류의 효율성
- Stage 1: 신중하게 차단 편향, 단일 토큰 결정
- Stage 2: 동일 프롬프트 + 다른 최종 지시, 추론 수행
- Stage 2 프롬프트는 Stage 1에서 거의 전부 **캐시 히트** -> 비용 효율적

### 멀티에이전트 핸드오프
- **아웃바운드 체크**: 서브에이전트에 위임 시 분류기 실행 (위임 시점에서 에이전트 선택 vs 사용자 요청 구분)
- **리턴 체크**: 서브에이전트 완료 시 전체 액션 히스토리 리뷰 (중간에 프롬프트 인젝션 방지)

### 거부 후 계속 (Deny-and-Continue)
- 거부 시 세션을 중단하지 않고, 더 안전한 대안을 찾도록 유도
- **연속 3회 거부** 또는 **총 20회 거부** 시 사람에게 에스컬레이션
- 헤드리스 모드(`claude -p`)에서는 프로세스 종료
- 0.4% FPR에서의 오탐은 단일 재시도로 복구 가능

## 9. 차단 예시 (내부 사고 로그 기반)

| 시나리오 | 차단 이유 |
|----------|----------|
| "clean up old branches" -> 원격 브랜치 삭제 | 요청이 모호, 비가역적 파괴 행위 |
| 인증 오류 후 환경변수/설정 파일에서 토큰 검색 | 다른 태스크용 자격 증명 탐색 |
| "cancel my job" -> 유사 이름 매칭으로 삭제 시도 | 에이전트가 추론한 매개변수, 다른 사람 소유 가능 |
| 디버깅용 GitHub Gist 생성 | 데이터 유출 (기밀 가능성) |
| 배포 사전 체크 실패 후 skip-verification 플래그 재시도 | 공유 인프라 안전 검증 우회 |

## 10. 향후 방향

- 실제 과잉행동 테스트셋 지속 확장
- 안전성과 비용 개선 반복
- 사용자에게 잔여 위험 인식, 자율 실행 환경/태스크에 대한 판단 촉구
- 분류기가 완벽할 필요 없이 가드레일 없는 것보다 **상당히 안전**하면 가치 있음
