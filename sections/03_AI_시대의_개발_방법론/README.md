# 섹션 3. AI 시대의 개발 방법론

> Claude Code를 소개한 뒤, "이 도구를 잘 쓰려면 방법론이 필요하다"는 동기를 부여하고, 각 방법론을 소개한 뒤 가장 효과적인 조합을 제시한다. 다음 섹션(하네스 엔지니어링)으로의 브릿지 역할.

---

## 핵심 메시지

> 다양한 AI 개발 방법론이 등장했지만, 현재 가장 강력한 조합은 **Spec + TDD**다. 스펙으로 의도를 명확히 하고, 테스트로 검증을 자동화한다. 이걸 시스템으로 구축하는 것이 하네스 엔지니어링이다.

---

## 왜 방법론이 필요한가

2025년 이전, 대부분의 개발자는 AI를 "고급 자동완성(fancy autocomplete)"으로 사용했다. 주석을 타이핑하면 제안이 나오고, 수락하거나 거부했다. 단순했다.

그러다 **에이전틱 코딩**이 등장했다 — AI가 계획을 세우고, 다단계 작업을 실행하고, 전체 기능을 작성할 수 있게 되었다. 갑자기 **병목이 바뀌었다**:
- 코드를 작성하는 것이 어려운 게 아니라
- **AI에게 무엇을 작성할지 알려주는 것**
- 그리고 **AI가 실제로 원하는 대로 했는지 확인하는 것**이 어려운 일이 되었다

그 결과, AI 시대에 맞는 다양한 개발 방법론이 등장했다.

### 타임라인

| 시기 | 사건 | 영향 |
|------|------|------|
| 2025.02 | Karpathy "Vibe Coding" 명명 | AI 코딩의 대중화, 문화적 전환점 |
| 2025 중반 | AI 생성 코드의 품질/보안 문제 부각 | 구조화된 방법론의 필요성 대두 |
| 2025 하반기 | SDD, BMAD 등 프레임워크 등장 | Vibe Coding의 한계에 대한 업계 대응 |
| 2026 초 | TDD + AI, Context Engineering 부상 | 성숙한 AI 개발 워크플로우의 정립 |

## 등장한 방법론들

### 구조화 수준 스펙트럼

```
낮은 구조화 ←────────────────────────────────→ 높은 구조화

  Vibe Coding  |  PDD  |  ADD  |  TDD+AI  |  SDD  |  BMAD
     탐색적      의도     협업      검증       계획     조직
```

### VDD — 바이브 코딩 (Vibe-Driven Development)

2025년 2월, Andrej Karpathy가 명명:
> "There's a new kind of coding I call 'vibe coding', where you fully give in to the vibes, embrace exponentials, and forget that the code even exists."

**방식**: 자연어로 원하는 것을 설명하고 AI가 모든 코드를 작성. "Accept All" 클릭. 에러 발생 시 에러 메시지를 그대로 복사-붙여넣기.

**문화적 영향**:
- Collins Dictionary 2025 올해의 단어 선정
- 검색량 6,700% 급증
- Y Combinator 2025 겨울 배치 25%가 코드의 95%를 AI로 생성

**적합한 경우**: 프로토타이핑, MVP, 주말 사이드 프로젝트, 아이디어 탐색

**현실적 문제**:
- AI 생성 코드의 약 45%에 보안 결함
- "3개월 블랙박스" — 만들고 3개월 후 아무도 작동 방식을 설명 못 함
- Linus Torvalds: "시작하는 데는 괜찮지만 유지보수에는 끔찍한 아이디어"

---

### PDD — 프롬프트 주도 개발 (Prompt-Driven Development)

**방식**: 프롬프트를 위시리스트나 채팅이 아닌, **검증 가능한 명세(contract)**로 취급.

**PDD 매니페스토**:
- "완료(done)"를 정의할 수 있을 때만 코드 작성
- 프롬프트가 측정 가능해질 때까지 반복
- 테스트는 심판(referee)이지 장식이 아니다

**좋은 PDD 프롬프트** — 프롬프트 자체가 계약서:
```
"장바구니 할인 계산 함수를 구현해줘.
- 입력: items[{price, quantity}], coupon_code(optional)
- 규칙: 5만원 이상 → 무료배송, 미만 → 배송비 3,000원
- 출력: { subtotal, discount, shipping_fee, total }
- 에러: 만료 쿠폰 → COUPON_EXPIRED, 할인 후 음수 불가
- 검증: 'SUMMER10' 적용 시 10% 할인, 4만원 주문 시 배송비 3,000원"
```

**나쁜 PDD 프롬프트**: `"할인 기능 만들어줘"`

PDD의 핵심은 **프롬프트 한 번에 입력·출력·규칙·에러·검증 조건까지** 모두 담는 것. 별도 문서 없이 프롬프트 자체가 명세이자 계약이다.

**장점**: 자연어로 접근성 높음, 비개발자도 참여 가능
**한계**: 좋은 프롬프트 작성 능력 필요, 복잡한 시스템에서 프롬프트만으로 충분한 명세 어려움

---

### ADD — 에이전트 주도 개발 (Agent-Driven Development)

**방식**: AI 에이전트와 인간이 **구조화된 프로세스**로 협업. 에이전트가 구현/문서화/테스팅을 처리, 인간(Editor)이 방향/전문성/비판적 사고를 제공.

> "ADD는 Vibe Coding이 성숙했을 때 되고 싶은 것이다." — Remo H. Jansen

**Vibe Coding과의 차이**:
- Vibe Coding: 자발적, 혼란적, 확장 불가능
- ADD: 구조적, 엄격하고, 엔터프라이즈급 시스템을 위해 설계

**핵심 마인드셋 전환**: "어떻게 구현할까?"에서 **"에이전트가 올바르게 구현하도록 어떻게 안내할까?"**

**에이전트 vs 인간 영역**:

| 에이전트가 하는 것 | 인간이 소유하는 것 |
|-------------------|-------------------|
| 코드 검색, 읽기, 작성 | 전략적 의사결정 (무엇을 만들지) |
| 셸 명령 실행, 테스트 | 아키텍처 선택 |
| 패키지 설치, 의존성 관리 | 보안 검증 |
| 문서 생성 | 최종 품질 검증 |

**장점**: 기능 개발 속도 극적 향상 (10x), 일관된 코드 스타일, 문서 자동 생성
**한계**: 강력한 DevOps 인프라 전제, 에이전트의 아키텍처 실수 가능

---

### TDD + AI — AI 시대의 테스트 주도 개발

**방식**: 인간이 실패하는 테스트를 먼저 작성하고, AI 에이전트가 테스트를 통과하는 코드를 구현. AI의 비결정적 출력을 결정적 테스트로 제어.

```
1. [인간] 실패 테스트(Red) 작성
2. [AI] 테스트를 통과하는 최소 코드(Green) 구현
3. [인간] 통과 코드를 감사
4. [AI] 통과 상태를 유지하며 리팩토링
5. 반복
```

**구체적 예시** — 같은 장바구니 할인을 TDD로 지시:
```
"장바구니 할인 계산을 TDD로 구현해줘.
1. 먼저 테스트만 작성: 기본 합계, 배송비, 쿠폰 할인
2. 테스트 실행해서 실패(Red) 확인
3. 테스트를 통과하는 최소한의 코드 작성
4. 테스트 통과(Green) 확인
5. 다음 기능의 테스트를 추가하고 반복"
```

→ 핵심은 **테스트가 먼저 "실패"해야 다음 단계로 넘어간다**는 것. 왜?
- AI에게 "코드 짜고 테스트도 짜줘"라고 하면? → 자기 코드에 맞는 약한 테스트를 작성 (치팅)
- TDD: 테스트 실패 확인이 강제되므로 치팅 불가. **기계가 자동으로 검증**한다.

SDD와의 차이: SDD는 **"무엇을 만들지"를 문서로 정의**하고 인간이 결과를 검토한다. TDD는 **"제대로 만들었는지"를 테스트가 자동 검증**한다. SDD는 방향을 잡고, TDD는 구현을 잡는다.

**핵심 원칙**:
- **테스트가 우리(cage)다**: AI의 비결정적 출력을 통제하는 역할
- **인간이 테스트, AI가 구현**: AI가 코드와 테스트를 동시에 작성하면 자기 결함을 확인하는 약한 테스트를 "치팅"으로 작성
- **한 번에 하나의 테스트**: 한꺼번에 생성하면 얕고 중복된 테스트
- **테스트를 수정하여 통과시키지 않는다**: 이 규칙 없이는 에이전트가 테스트 어서션을 조정

> "에이전트가 Red에서 Green으로 가는 것을 지켜보는 것은, 코드의 모든 줄을 읽지 않고도 신뢰를 확보하는 방법이다." — LoreAI

**실제 수치**: 버그 40~80% 감소 (2025 DORA 보고서)
**주요 옹호자**: Kent Beck (TDD 창시자), Simon Willison ("테스트-우선 개발은 코딩 에이전트에 환상적으로 적합하다")

#### AI는 실제로 어떻게 치팅하는가

AI에게 "테스트 통과시켜"라고만 하면 통과를 만들어낸다 — 정직한 방법이 아닐 수도 있다. 실제 관찰되는 3가지 패턴:

1. **테스트를 삭제/skip/xfail 처리** — 구현이 막히면 테스트 자체를 비활성화
2. **구현을 먼저 쓰고 거기에 맞춰 테스트 작성** — 코드와 테스트를 동시에 쓰면 "자기 코드를 확인하는 약한 테스트"가 됨
3. **assert 약화** — 값 검증을 타입 검증으로, `assertEqual`을 `assertTrue`로 슬쩍 바꿈

> "The genie doesn't want to do TDD." — Kent Beck

그래서 TDD+AI는 프롬프트 한 줄로 되지 않는다. **프로세스를 강제할 장치**가 필요하다.

#### 강제력의 스펙트럼

같은 TDD 규칙도 어디에 어떻게 박느냐에 따라 강제력이 다르다.

```
프롬프트  <  문서(CLAUDE.md)  <  슬래시 커맨드  <  단계별 에이전트 격리  <  자동 차단 훅
  약함 ─────────────────────────────────────────────────────────────────→  강함
```

- **문서**: "TDD를 지켜주세요" — AI가 무시할 수 있다
- **슬래시 커맨드/스킬**: 특정 트리거에서 TDD 워크플로우를 자동 주입
- **에이전트 격리**: 테스트를 쓰는 AI와 구현을 쓰는 AI를 **분리된 컨텍스트**로 돌려 치팅을 물리적으로 불가능하게 만든다 (코드를 못 보는 AI는 코드에 맞춘 테스트를 쓸 수 없다)
- **훅**: 테스트 없이 구현 파일을 수정하려 하면 도구 호출 자체를 차단

팀의 요구 수준에 맞는 층까지만 올리면 된다. 개인 프로젝트는 문서로 충분하고, 조직 표준은 훅이 필요하다.

#### CLAUDE.md에 박을 TDD 규칙 (예시)

추상적인 "TDD 하세요" 대신 AI가 검증 가능한 규칙으로 적는다:

```markdown
## TDD Rules
1. 모든 새 기능은 RED → GREEN → REFACTOR 순서를 따른다. 단계 건너뛰기 금지.
2. RED에서는 실패하는 테스트를 하나만 쓴다. 실제 실패를 확인한 뒤에 진행한다.
3. GREEN에서는 테스트를 통과시키는 최소 코드만 쓴다. 일반화 금지.
4. 테스트를 삭제/skip/약화시켜 통과시키지 않는다.
5. 구조 변경(리네임/추출)과 행위 변경(기능 추가)을 같은 커밋에 섞지 않는다.
```

규칙마다 **"왜"**가 없으면 AI가 맥락에서 벗어날 때 지키지 않는다. 규칙 옆에 한 줄로 이유를 붙여두면 훨씬 안정적으로 지켜진다.

### SDD — 스펙 주도 개발 (Spec-Driven Development)

**방식**: 구조화되고 기계 판독 가능한 명세를 개발의 중심에 놓는다. **코드가 아닌 스펙이 소스 오브 트루스.**

Vibe Coding이 확산된 후 한계가 뚜렷해지면서 등장한 **업계의 궤도 수정(course correction)**.

**워크플로우**:
```
1. [인간] 요구사항을 구조화된 스펙(Markdown/YAML/JSON)으로 작성
2. [인간] 아키텍처 결정, 제약조건, 기술 스택 명시
3. [AI] 스펙을 읽고 구현 계획 제안
4. [인간] 계획 검토 및 승인
5. [AI] 스펙에 따라 코드 생성
6. [자동화] 스펙 준수 여부 검증
7. 반복
```

**스펙 예시** — 같은 장바구니 할인을 구조화된 문서로:
```markdown
# Feature: 장바구니 할인 계산

## Requirements
- 상품 목록(price, quantity)을 받아 합계 계산
- 쿠폰 코드 적용 시 할인율에 따라 차감
- 5만원 이상 주문 시 무료배송, 미만 시 3,000원

## Constraints
- 쿠폰은 1회만 적용 가능
- 할인 후 금액이 음수가 될 수 없음
- 기존 PostgreSQL 사용

## Acceptance Criteria
- [ ] 쿠폰 없이 정상 합계 계산
- [ ] 유효 쿠폰 적용 시 할인 반영
- [ ] 만료 쿠폰 → COUPON_EXPIRED 에러
- [ ] 5만원 이상 → shipping_fee = 0
```
→ AI에게: `"specs/cart-discount.md 읽고 구현해줘"`

다른 방법론과의 차이:
- vs PDD: PDD는 프롬프트에 모든 걸 담지만, SDD는 **별도 파일에 구조화된 스펙을 먼저 작성**. 스펙 파일이 버전 관리되고, 팀이 공유하고, 여러 세션에 걸쳐 AI가 반복 참조할 수 있다.
- vs TDD: TDD는 테스트로 "제대로 구현했는지"를 기계가 검증하지만, SDD는 **"무엇을 만들지" 자체를 문서로 정의**하고 인간이 검토한다. 아키텍처·기술 스택·제약 같은 큰 그림은 테스트로 잡을 수 없다.

**장점**: AI에게 명확한 지침 제공, 환각 감소, 팀 간 일관성, 유지보수성 높음
**한계**: 초기 스펙 작성 노력, 빠른 프로토타이핑에 부적합

#### 스펙의 무게 — 프로젝트 크기에 맞춰라

"스펙 한 장이면 된다"도, "모든 걸 스펙에 박아라"도 정답이 아니다. 피처 복잡도·팀 규모에 따라 스펙의 무게를 조절한다.

| 무게 | 구조 | 언제 |
|------|------|------|
| **경량** | 요구사항 + 수용 기준만 (1페이지) | 혼자, 작은 피처 |
| **표준** | 요구사항 → 설계 → 작업 분할 (3파일) | 팀 피처 개발 |
| **풀** | 원칙 → 스펙 → 계획 → 데이터 모델 → API 계약 → 태스크 | 크로스팀, 엔터프라이즈 |

핵심은 **스펙이 많다고 좋은 게 아니다**. 혼자 쓰는 사이드 프로젝트에 8파일 스펙은 오버킬이고, 팀 개발에 한 줄 프롬프트는 부족하다.

#### SDD 실전 워크플로우 (일반화된 3단계)

도구는 달라도 성숙한 SDD 도구들이 공통으로 취하는 패턴:

```
1. SPECIFY   — WHAT/WHY만 쓴다. HOW는 금지.
               요구사항, 사용자 스토리, 수용 기준.
               모호한 부분은 [NEEDS CLARIFICATION] 마커로 명시.

2. PLAN      — 그제서야 HOW. 기술 스택, 아키텍처, 데이터 모델, 제약.
               조직 원칙(Constitution)에 위배되지 않는지 게이트 통과.

3. TASKS     — 계획을 병렬 가능한 작업 단위로 분해.
               작업 ↔ 요구사항 매핑을 남겨 트래킹.
```

각 단계가 **파일로 남고, 브랜치에 커밋되고, AI가 여러 세션에 걸쳐 참조**한다. 채팅 속 프롬프트는 휘발되지만 스펙 파일은 살아남는다.

#### 장치 하나: "NEEDS CLARIFICATION" 마커

SDD 도구들이 공통으로 쓰는 장치. AI가 모호한 부분을 **추측해서 채우지 못하게** 강제한다.

```markdown
## Requirements
- 상품 목록을 받아 합계를 계산한다
- 5만원 이상 주문 시 무료배송, 미만 시 배송비 부과
  [NEEDS CLARIFICATION: 배송비 금액? 지역별 차등?]
- 쿠폰 코드 적용 시 할인
  [NEEDS CLARIFICATION: 쿠폰 중복 적용 허용?]
```

AI가 이 마커를 만나면 구현을 멈추고 사람에게 묻는다. "환각의 원천"을 사전에 봉쇄하는 값싼 장치.

#### 장치 둘: 버그 수정용 전용 스펙 포맷

버그는 피처와 다르다. 포맷도 달라야 한다.

```markdown
# Bug: 결제 후 장바구니가 비워지지 않음

## Reproduction
1. 상품 담기 → 결제 완료
2. 홈으로 돌아오면 장바구니에 상품 남아있음

## Current behavior
결제 성공 이벤트 후에도 cart state가 유지됨

## Expected behavior
결제 성공 시 cart state가 빈 배열로 초기화

## Constraints (건드리면 안 되는 것)
- 결제 실패 시에는 cart가 유지되어야 함 (기존 동작)
- 게스트 장바구니 로직은 변경 금지
```

**Constraints 필드가 핵심**. AI에게 "고쳐야 할 것"만큼 "건드리지 말아야 할 것"을 알려줘야 무분별한 리팩터링을 막을 수 있다.

#### CLAUDE.md를 스펙으로 쓰는 경량 패턴

별도 파일 없이 CLAUDE.md 자체가 프로젝트 스펙이 될 수 있다. 핵심은 **Always / Ask first / Never 3분할**:

```markdown
# Project Spec

## Tech Stack
- React 18, TypeScript, PostgreSQL

## Boundaries
- Always: 커밋 전 테스트 실행, 타입 에러 0 유지
- Ask first: DB 스키마 변경, 외부 API 추가, 의존성 추가
- Never: 시크릿 커밋, 테스트 skip/삭제, 프로덕션 DB 직접 쿼리
```

AI가 **망설일 수 있는 영역을 미리 선언**하는 것. "이건 해도 돼? 물어봐? 하지 마?"를 매번 판단하게 두지 않는다.

## 결론: Spec + TDD 조합이 가장 강력하다

방법론들을 살펴봤으니, 핵심으로 가보자.

한 문장으로: **SDD는 잘못된 것을 만드는 걸 막고, TDD는 올바른 것을 잘못 만드는 걸 막는다.**

AI에게 코드를 잘 시키려면 **두 가지가 동시에** 필요하다:

**1. 의도를 명확히 전달하는 것 → Spec (SDD)**
- "로그인 기능 만들어줘"가 아니라 요구사항, 제약, 수용 기준을 구조화
- AI가 할 수 있는 실수의 범위가 극적으로 줄어듦

**2. 결과를 자동으로 검증하는 것 → Test**
- 스펙을 아무리 잘 써도, AI가 그대로 구현했는지 확인해야 한다
- Red-to-Green 전환을 지켜보는 것만으로 코드의 모든 줄을 읽지 않고도 신뢰 확보

**스펙 없이 TDD만 하면**: 테스트는 있지만 전체적인 방향이 없다. 나무는 보지만 숲을 못 본다.
**TDD 없이 스펙만 쓰면**: 의도는 명확하지만 AI가 실제로 스펙대로 구현했는지 검증할 수단이 없다.

**둘을 합치면**:
- 스펙이 **"무엇을"** 정의하고
- 테스트가 **"정말로 그렇게 됐는지"** 검증한다

#### 결합 워크플로우

스펙과 테스트가 각자 다른 층에서 계약을 강제하는 구조:

```
1. [인간] 스펙에 계약 정의      ← "무엇을 만들지"
              ↓
2. [인간] 스펙에서 시나리오 추출  ← 테스트 가능한 단위로 분해
              ↓
3. [AI] 실패 테스트 작성 (Red)  ← 구현 전 행위 어서션
              ↓
4. [AI] 최소 코드로 통과 (Green) ← 스펙 + 테스트가 이중 안전망
              ↓
5. [AI] 스펙을 안전망 삼아 리팩터
```

**이중 안전망의 효과**: 스펙은 AI가 "엉뚱한 걸 만드는 것"을 막고, 테스트는 AI가 "만든 걸 잘못 만드는 것"을 막는다. 둘 중 하나만 있으면 AI가 빠져나갈 틈이 남는다.

---

## 그런데 이걸 매번 수동으로 할 것인가?

Spec + TDD가 강력하다는 건 알겠다. 하지만:
- 매 프로젝트마다 스펙 템플릿을 새로 만들고
- 매 세션마다 "테스트 먼저 써"라고 지시하고
- 매번 컨벤션을 설명하고

이걸 **시스템으로 구축**하면 어떨까?

→ 스펙 템플릿을 계획 문서(`specs/*.md`, `PLAN.md`)로 정착시키고
→ Skills로 TDD 워크플로우를 패키징하고
→ Hooks로 테스트 자동 실행을 걸고

**이것이 바로 하네스 엔지니어링이다.**

## 전통적 방법론과의 관계

AI 시대 방법론은 기존 방법론의 진화:

| 전통 방법론 | AI 시대 대응 |
|------------|-------------|
| Waterfall | SDD (구조화된 사전 계획, 하지만 반복적) |
| Agile/Scrum | ADD (스프린트 + 에이전트 협업) |
| XP (Extreme Programming) | TDD + AI (페어 프로그래밍 → 인간+AI 페어링) |
| Lean | Vibe Coding (최소 실행 가능 제품 빠른 검증) |
| DevOps | Context Engineering (컨텍스트의 CI/CD) |

### 변하지 않는 것들

1. **관심사의 분리**: 모듈러 아키텍처가 AI 에이전트에게도 필수
2. **테스팅의 가치**: "선택에서 필수"로 격상
3. **문서화의 가치**: "인간을 위한 문서"에서 "AI를 위한 실행 가능한 명세"로 진화
4. **코드 리뷰**: "모든 줄 읽기"에서 "전략적 검증"으로 역할 변화
