# 섹션 6. 멀티 에이전트 활용

> 섹션 4에서 "하네스는 컨텍스트를 관리하는 시스템"이라고 했다면, 멀티 에이전트는 그 하네스의 **가장 강력한 확장**이다. 하나의 모델이 모든 것을 하려는 순간 컨텍스트가 오염되고 신뢰성이 무너진다. 해답은 **역할을 쪼개는 것**이다.

---

## 핵심 메시지

> "하나의 에이전트가 하나의 일을 하게 하라."
> "수 시간 동안 실행되는 단일 에이전트 대신, 각각 5분씩 실행되는 다수의 에이전트를 쓰면 장시간 실행되는 시스템이 장시간 에이전트 없이도 만들어진다." — Paul Fruitful (Claude Code 하네스 분석)
> "핵심은 에이전트 방식이 아니라 **프로세스의 경계, 책임, 역할 분리**다." — Jae Heo (Toss)

---

## 왜 멀티 에이전트인가 — 단일 에이전트의 세 가지 벽

단일 에이전트가 오래 일할수록 필연적으로 맞닥뜨리는 세 가지 벽:

### 1. 컨텍스트의 벽
에이전트가 파일을 읽고, 테스트를 돌리고, 로그를 수집하는 동안 **컨텍스트가 쓰레기로 채워진다**. 섹션 4에서 본 Context Rot·Distraction·Confusion이 바로 여기서 발동한다. 50k 토큰부터 이미 성능이 썩기 시작한다.

### 2. 역할의 벽
"테스트를 쓰고, 구현하고, 리뷰하고, 리팩터하라"를 한 에이전트에게 맡기면 전부 어설프게 한다. 특히 **자기가 쓴 코드를 자기가 리뷰**하면 blind spot이 그대로 남는다 — 섹션 3의 AI 치팅 패턴의 뿌리다.

### 3. 신뢰성의 벽
각 단계 성공률 95%, 20단계 연쇄 → 전체 성공률 36% (섹션 4의 신뢰성 수학). 단일 긴 체인은 **수학적으로 실패한다**.

**해법은 하나 — 하나의 에이전트가 하나의 일만 하게 한다.** 컨텍스트를 나누고, 역할을 나누고, 검증을 분리한다. 이것이 멀티 에이전트의 본질이다.

---

## 단일 에이전트 → 에이전트 팀 — 진화의 층위

멀티 에이전트는 하나의 패턴이 아니라 **점점 복잡해지는 스펙트럼**이다.

```
1. Single Agent        — 모든 일을 한 컨텍스트에서
2. Sub-Agent           — 격리된 컨텍스트로 "심부름" (단방향)
3. Orchestrator        — 계획자 + 실행자들 (1:N 위임)
4. Parallel Agents     — 병렬 작업 + 공유 상태
5. GAN-Style           — 생성자 ↔ 평가자 적대적 루프
6. Agent Teams         — 양방향 대화가 가능한 팀
```

층이 올라갈수록 **힘은 세지지만 조율 비용도 커진다**. 모든 작업을 Agent Teams로 할 필요는 없다. 대부분의 일상 작업은 2~3번 층에서 끝난다.

## 패턴 1 — Sub-Agent: 심부름 보내기

**가장 자주 쓰는 패턴이자 가장 과소평가된 패턴.** 메인 에이전트가 "가서 이것만 알아보고 요약만 가져와" 하고 서브에이전트를 띄우는 구조.

### 왜 강력한가
- **컨텍스트 격리**: 서브에이전트는 자신만의 컨텍스트 윈도우에서 작업한다. 파일 50개를 뒤져도 메인 컨텍스트는 오염되지 않는다. 요약 1~2천 토큰만 돌아온다
- **도구 제한**: 서브에이전트에게 읽기 전용만 허용할 수 있다. 탐색용 에이전트가 실수로 파일을 쓰는 사고가 원천 차단된다
- **모델 라우팅**: 단순 탐색은 Haiku, 복잡한 분석은 Sonnet/Opus로 비용 최적화
- **방향성 강제**: "Test Writer는 구현 코드를 못 본다", "Implementer는 스펙을 못 본다" 같은 **정보 격리**로 AI 치팅을 물리적으로 막는다 (섹션 3)

### 주요 용도
- **탐색 (Explore)**: "이 코드베이스에서 JWT 관련 파일 다 찾아서 요약" → Haiku 서브에이전트 한 방
- **검증 (Verify)**: "전체 테스트 돌리고 실패한 것만 보고해" → 로그 전체가 아니라 핵심 요약만
- **대용량 로그 파싱**: "이 10MB 에러 로그에서 스택트레이스 3개만 뽑아"
- **보안 리뷰**: "이 PR에서 보안 이슈만 체크" — 스타일 코멘트는 무시

### 설계 팁
- 서브에이전트의 `description` 필드에 **"언제 이걸 쓰는지"**를 명확히 쓴다. 메인 에이전트는 이걸 읽고 자동 위임한다
- 출력 형식을 강제한다. 자유 서술보다 **JSON 또는 구조화된 마크다운**이 다음 단계에서 재사용하기 쉽다
- **"요약만 반환하라"**를 시스템 프롬프트에 명시. 서브에이전트가 전체 로그를 다시 메인으로 토해내면 격리의 의미가 사라진다

> **격언**: "메인 에이전트의 컨텍스트는 금이다. 서브에이전트가 만드는 것은 요약이다."

## 패턴 2 — Orchestrator: 계획자 + 실행자들

하나의 에이전트가 **계획을 세우고**, 그 계획을 쪼개서 **여러 실행자**에게 나눠준다. 섹션 4의 Plan-Critic-Build 루프의 멀티 에이전트 버전.

### 3단계 구조
```
                Planner
                   │
      ┌────────────┼────────────┐
      ↓            ↓            ↓
  Executor A   Executor B   Executor C
      │            │            │
      └────────────┼────────────┘
                   ↓
               Verifier
```

### 누가 무엇을 하는가
- **Planner (Opus 같은 고성능)**: 1~4문장 요구사항을 전체 스펙으로 확장, 작업을 독립 가능한 단위로 분해
- **Executor (Sonnet)**: 자기에게 할당된 작업만 구현. 다른 Executor가 뭘 하는지 모름
- **Verifier**: 통합 결과가 원래 스펙에 부합하는지 검증. 실패하면 Planner로 피드백

### 핵심 원칙
- **계획과 실행은 같은 컨텍스트에 두지 않는다** — 계획 수립의 수다가 실행 컨텍스트를 오염시키지 않도록
- **Executor는 "자신의 작업" 외에는 모른다** — 잘못된 공유가 Context Clash를 만든다
- **병렬 가능한 것만 병렬로** — Planner가 의존성을 판단해 `[P]` 마커가 붙은 작업만 동시 실행

### 적합한 작업
- 여러 파일에 걸친 리팩터링 (파일마다 Executor 하나씩)
- 풀스택 피처 구현 (DB 스키마 / API / UI / 테스트를 각자)
- 마이그레이션 (독립적인 모듈을 병렬 이전)

## 패턴 3 — Parallel Agents: 공유 코드베이스에서 동시 작업

Orchestrator가 "명령 체계"라면 Parallel Agents는 "평면 조직"이다. 여러 에이전트가 **같은 목표를 향해 독립적으로** 일한다.

### 작동 원리 (Nicholas Carlini의 16-에이전트 C 컴파일러 사례에서 정리)
1. **태스크 잠금**: 각 에이전트가 `current_tasks/` 디렉토리에 파일을 써서 작업을 "찍는다". Git 동기화가 중복을 막는다
2. **역할 분화**: 에이전트마다 다른 목적. 한 명은 중복 통합, 한 명은 성능, 한 명은 비판, 한 명은 문서화
3. **작업 후 동기화**: upstream pull → merge → push → 잠금 해제
4. **격리된 워크트리**: 각 에이전트가 `git worktree`로 자기 공간에서 일하고 완성된 결과만 머지

### 주의점
- **충돌 처리**가 핵심. 같은 파일을 두 에이전트가 동시에 건드리면 머지 지옥
- **공유 상태를 최소화**. 에이전트 간 메시지를 파일로 주고받는 것이 스레드/큐보다 안전
- **관찰 가능성**: 16개가 동시에 돌면 무슨 일이 일어나는지 모른다. HUD나 로그 집계가 필수

### 언제 쓰는가
- **Greenfield 대규모 프로젝트**: 초기 뼈대를 빠르게 만들 때
- **독립 모듈이 많은 코드베이스**: 마이크로서비스, 독립 패키지들
- **탐색적 작업**: "여러 접근을 동시에 시도하고 가장 좋은 것 채택"

## 패턴 4 — GAN-Style: 생성자 ↔ 평가자

AI가 자기 결과물을 **적대적 평가자**의 눈으로 반복 검증하는 패턴. GAN(Generative Adversarial Network)에서 이름을 빌렸다.

### 루프
```
Generator가 결과물 생성
        ↓
Evaluator가 루브릭에 따라 채점 + 피드백
        ↓
Generator가 피드백 반영해 재생성
        ↓
(점수가 임계치를 넘을 때까지 반복)
```

### 왜 강력한가
- Generator 혼자서는 **자기 결과를 객관적으로 못 본다**. 같은 실수를 반복한다
- Evaluator가 **별도 시스템 프롬프트**를 가지면 같은 모델도 전혀 다른 관점으로 본다
- 루브릭이 명시적이므로 **"좋다/나쁘다"가 측정 가능**해진다

### Anthropic의 실제 활용 예 (일반화된 교훈)
- **프론트엔드 품질**: Evaluator에 Playwright MCP를 쥐어주고 **실제 브라우저에서 인터랙션**하며 채점. 정적 스크린샷이 아니라 실행 중인 웹페이지를 본다. 5~15회 반복으로 평범한 랜딩이 3D 공간 경험으로 진화
- **풀스택 생성**: Planner(1문장 → 스펙) → Generator(구현) → Evaluator(Playwright로 UI·API·DB 모두 테스트). 단일 에이전트 20분·$9·거의 동작 안함 vs 풀 하네스 6시간·$200·완성도 높음 — **2배 개선이 아니라 능력의 위상 전환**

### 설계 원칙
- **루브릭을 명시적으로**: "좋은 디자인"이 아니라 "간격 일관성 / 타이포 대비비 / 색상 조화 / 독창성" 4차원 가중 평가
- **Evaluator는 Generator의 작업 과정을 모른다**: 최종 결과물만 본다. 변명 기회를 주지 않는다
- **종료 조건을 정의**: "N회 반복 또는 점수 X 달성". 무한 루프 방지

## 패턴 5 — Agent Teams: 양방향 대화

앞 4개가 "명령-수행" 구조라면, Agent Teams는 **팀원끼리 서로 메시지를 주고받는** 구조다. 서브에이전트가 "시켜놓고 결과만 받는" 것이라면, Agent Teams는 "같이 토론하고 합의한다".

### Sub-Agent와의 차이

| 구분 | Sub-Agent | Agent Teams |
|------|-----------|-------------|
| 통신 | 단방향 (요청 → 결과) | 양방향 (대화) |
| 협업 | 지시받은 것만 수행 | 서로 의견 교환, 재질문 |
| 구조 | 트리 | 그래프 |
| 용도 | 명확한 하위 작업 | 모호한/창발적 문제 |

### 동적 팀 구성의 예 (일반 패턴)
- **경쟁사 분석**: Researcher 3명이 각자 다른 각도로 병렬 탐색 → Consultant가 분석 프레임 수립 → Editor가 최종 리포트
- **콘텐츠 제작**: Writer ↔ Editor 반복 개선, 동시에 Fact-Checker가 병렬 검증
- **아키텍처 결정**: CTO-level 에이전트가 주재, Backend/Frontend/DevOps 에이전트가 각자 입장 제시, 합의 도출

### 성숙한 팀 구조의 특징
- **역할 기반 모델 분배**: 판단은 Opus, 실행은 Sonnet, 탐색은 Haiku — 비용 예측 가능
- **자동 수정 루프**: Worker 구현 → QA 검증 → Support가 자동 수정 → QA 재검증
- **공유 컨텍스트 뱅크**: 팀원 공통 지식(프로젝트 스펙, 제약)은 중앙에 두고 참조
- **관찰 가능성**: 팀원 간 대화를 Slack·Discord로 미러링 (실제 운영 시 반드시 필요)

### 주의
- **조율 비용이 급증**한다. 3명까지는 이득, 10명이 넘어가면 서로 기다리는 시간이 작업 시간을 넘긴다
- **"팀이면 다 좋다"는 환상을 경계**하라. 단순 작업에는 Single Agent가 빠르다
- **언제 멈출지를 정의**해야 한다. 팀 대화는 자연스럽게 수렴하지 않는다

## 멀티 에이전트 설계 4대 원칙

패턴이 무엇이든 공통으로 지켜야 하는 설계 원칙:

### 1. 컨텍스트 격리 (Context Isolation)
**각 에이전트는 자기 일에 필요한 컨텍스트만 본다.** 메인 컨텍스트는 최종 결정과 요약만 담는다. 서브 컨텍스트의 "수다"는 메인으로 흘러나오지 않는다.

### 2. 역할 경계의 명시화 (Role Boundary)
각 에이전트의 **description에 "무엇을 하고 무엇을 하지 않는지"**를 쓴다. 모호한 경계는 중복 작업과 공백을 동시에 만든다.
```
좋음: "보안 이슈만 본다. 스타일/성능은 다른 에이전트 담당."
나쁨: "코드 리뷰를 잘 해준다."
```

### 3. 사전 모호성 제거 (Ambiguity Removal Before Execution)
Ralphton 대회 우승 사례의 교훈: **개발 전에 AI 에이전트 간 133회의 Q&A**로 설계 모호성을 사전에 제거했다. 실행 시작 후에 모호성을 발견하면 이미 늦다. Sub-Agent를 쓸 때도 "실행 전 질문 단계"를 넣는다.

### 4. 검증 주체 분리 (Separate Verifier)
**생성한 에이전트가 검증을 하지 않는다.** Self-review는 blind spot을 남긴다. 별도 에이전트가, 별도 컨텍스트에서, 별도 기준으로 검증한다.

## 흔한 실수 5가지

1. **"다 팀으로 해보자"** — 단순 작업에 팀을 쓰면 조율 오버헤드가 이득을 먹는다. 대부분의 일은 Sub-Agent 하나로 충분하다
2. **역할 없는 복제** — "에이전트 10개가 같은 프롬프트로 같은 일을 한다"는 팀이 아니다. 그냥 비싼 재시도다
3. **공유 컨텍스트 과잉** — "모든 에이전트가 모든 것을 본다" → Context Confusion + Clash의 원천. 격리가 기본값이어야 한다
4. **검증 없는 오케스트레이터** — Planner → Executor만 있고 Verifier가 없으면, 실패가 누적되어 최종 결과에서만 드러난다
5. **관찰 불가능한 팀** — 3명 이상의 에이전트가 동시에 돌면 상황을 모른다. HUD·로그·Slack 미러링 없이는 디버깅 불가

## "5분 에이전트" 철학 — 긴 에이전트보다 짧은 에이전트 여럿

멀티 에이전트의 가장 반직관적인 교훈:

> "수 시간 동안 실행되는 단일 에이전트 대신, 각각 5분씩 실행되는 다수의 에이전트를 순차적/비동기적으로 운영한다. 그 시간을 모두 합하면, 장시간 실행되는 에이전트 없이 장시간 실행되는 시스템을 얻는다."

왜 이게 이기는가:
- **실패 지점이 짧다**: 5분짜리가 실패하면 5분만 손해. 2시간짜리가 실패하면 2시간이 날아간다
- **컨텍스트가 늘 신선**하다: 길이가 50k를 넘기 전에 에이전트가 끝난다. Context Rot 없음
- **재시도 가능**: 짧은 단위는 멱등성을 설계하기 쉽다
- **관찰 가능**: 짧은 단위는 입출력을 보고 판단할 수 있다

**발표 포인트**: "Claude Code가 한 시간째 뭔가 하고 있는데 뭘 하는지 모르겠다"면, 그건 멀티 에이전트로 쪼개야 한다는 신호다.

## Claude Code에서의 구현 — 무엇을 쓰면 되는가

이론을 Claude Code 도구에 매핑하면:

| 패턴 | Claude Code 구현 |
|------|-----------------|
| Sub-Agent | `.claude/agents/*.md` 커스텀 서브에이전트, 내장 `Explore`/`Plan`/`general-purpose` |
| Orchestrator | Plan Mode(Shift+Tab 2회) → Sub-Agent 위임 |
| Parallel Agents | Git Worktree 격리 + 각 워크트리에서 독립 세션 |
| GAN-Style | 생성 서브에이전트 + 평가 서브에이전트를 Hook으로 체이닝 |
| Agent Teams | Claude Code의 Agent Teams 기능 (research preview) 또는 커뮤니티 플러그인 |

구성 파일 최소 예시 (`.claude/agents/security-reviewer.md`):
```markdown
---
name: security-reviewer
description: 보안 이슈만 본다. 스타일·성능은 다루지 않는다. 코드 변경 직후 자동 위임.
tools: Read, Grep, Glob
model: sonnet
---

당신은 보안 전문 리뷰어다.
- OWASP Top 10 기준으로 점검
- 각 지적에 파일:라인 첨부
- Critical / Warning / Info 세 등급으로 분류
- 스타일, 성능, 가독성 지적은 하지 않는다
```

핵심은 **description에 "언제 쓰는지"와 "무엇을 안 하는지"를 같이 쓰는 것**. 메인 에이전트는 이걸 보고 자동 위임한다.

## 발표용 한 장 요약

> **멀티 에이전트는 "더 많은 AI"가 아니라 "더 좁은 역할의 AI 여럿"이다.**
>
> - 컨텍스트를 쪼갠다 → 오염을 막는다
> - 역할을 쪼갠다 → 치팅을 막는다
> - 검증을 쪼갠다 → blind spot을 막는다
> - 시간을 쪼갠다 → 실패 비용을 줄인다
>
> "핵심은 에이전트 방식이 아니라 프로세스의 경계, 책임, 역할 분리다."
