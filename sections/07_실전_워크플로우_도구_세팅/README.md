# 섹션 7. 실전 워크플로우 & 도구 세팅 — 다 지키는 건 불가능하다, 대신 잘 만든 것을 쓴다

> 섹션 4에서 하네스와 컨텍스트 엔지니어링을, 섹션 6에서 멀티 에이전트 패턴을 봤다. 그리고 솔직한 문제에 도달한다. **이걸 매일 다 지키는 건 불가능하다.** 이 섹션은 "그럼 어떻게 할 것인가"에 대한 현실적인 답이다.

---

## 핵심 메시지

> "원리를 이해한 사람은 **다 직접 만들 필요가 없다**. 이미 누군가가 그 원리를 플러그인으로 패키징해뒀다."
> "도구를 잘 고르는 것이 도구를 직접 만드는 것보다 생산성이 높은 경우가 많다."
> "다만 **원리를 모르는 채로 플러그인을 쓰면** 같은 자리에서 같은 실수를 반복한다. 원리가 먼저, 플러그인은 다음이다."

---

## 솔직한 고백 — 앞의 내용을 다 지키는 건 불가능하다

지금까지 이 발표에서 다룬 것들을 세어보자.

- **CLAUDE.md**를 프로젝트·팀·개인 3층위로 설계한다
- **Skill**을 "무엇을" "언제" 발동할지 정의해 패키징한다
- **Hook**으로 포맷·린트·검증·핸드오프 자동화를 건다
- **서브에이전트**를 역할별(탐색·리뷰·테스트 작성·구현·검증)로 쪼갠다
- **Plan Mode**로 계획과 실행을 분리한다
- **Git Worktree + 멀티 세션**으로 병렬성을 확보한다
- **이슈 트래커**와 MCP로 작업 단위를 코드 밖에서 고정한다
- **컨텍스트를 4가지 실패 모드**로부터 방어한다
- **암묵지**를 한 줄 한 줄 문서로 뽑아낸다
- **모델 라우팅**으로 비용을 최적화한다

솔직해지자. **대부분의 개인이 이걸 다 세팅해서 일하는 건 불가능하다.** 설령 한 번 세팅해도 업데이트되지 않고, 팀에 공유되지 않고, 몇 달 뒤에는 누가 만들었는지도 기억나지 않는다.

그럼 어떻게 할 것인가. 답은 두 가지다.

1. **원리는 이해한다** — 섹션 4~6까지를 이해한 사람만이 플러그인을 제대로 쓸 수 있다
2. **구현은 위임한다** — 이미 잘 만들어진 것을 쓴다. 직접 만드는 건 딱 필요한 것만

"원리 없이 플러그인만" = 블랙박스 의존. "플러그인 없이 원리만" = 번아웃. **둘 다 필요하다.**

## 플러그인 생태계 — 커뮤니티가 이미 만들어둔 것들

Claude Code의 플러그인 마켓플레이스에는 이미 수백 개의 커뮤니티 플러그인이 있다. 그중 우리가 이 발표에서 다룬 원리를 **거의 그대로 패키징한** 것이 있다. 멋진 분들이 고생해서 만들어둔 것을, 우리는 한 줄 명령어로 설치해서 쓸 수 있다.

대표적인 축:

| 축 | 플러그인 카테고리 예시 |
|----|----------------------|
| **멀티 에이전트 오케스트레이션** | Oh My Claude Code (OMC), teammate-assemble |
| **세션/메모리 관리** | claude-mem, session-wrap |
| **복합 엔지니어링** | Compound Engineering Plugin (Every.to) |
| **요구사항 명확화** | clarify |
| **다중 모델 심의** | agent-council, claude-council |
| **코드베이스별 베스트 프랙티스** | react-best-practices, Vue/Rails 전용 Skill 등 |

이 중에서 **OMC**를 이 섹션의 메인 예시로 고른다. 이유는 간단하다. OMC 하나가 **섹션 4~6에서 다룬 원리의 거의 전부를 커버**하기 때문이다. OMC를 깊게 보는 것이 "플러그인으로 원리를 실현하는 법"을 이해하는 가장 빠른 길이다.

> 참고로 OMC는 한국 개발자(Yeachan Heo)가 만들었고, GitHub Trending 1위를 기록했다. 한국 커뮤니티가 세계 Claude Code 생태계에서 주요 기여자 중 하나라는 증거이기도 하다.

## OMC — Oh My Claude Code란 무엇인가

### 한 줄 정의

**OMC는 Claude Code 위에서 돌아가는 "Teams-first 멀티 에이전트 오케스트레이션 플러그인"이다.** 슬로건은 `"Don't learn Claude Code. Just use OMC."` — 사용자는 자연어로 일을 던지기만 하고, OMC가 섹션 4~6에서 다룬 원리들을 뒤에서 자동으로 적용한다.

### OMC가 해결해주는 것들 (섹션 매핑)

| 이 발표의 원리 | OMC에서의 구현 |
|---------------|---------------|
| 멀티 에이전트 역할 분리 (섹션 6) | 29개 이상의 사전 정의 에이전트 (architect / executor / critic / tester / debugger 등) |
| 모델 라우팅 (섹션 4) | 작업 난이도에 따라 Haiku/Sonnet/Opus 자동 선택, 토큰 30~50% 절감 |
| 계획-비평-실행 루프 (섹션 4) | **`/ralplan`** — 합의 기반 계획 단계. architect가 계획하고 critic이 별도로 비평한 뒤 실행 허가 |
| 병렬 에이전트 (섹션 6) | `/ultrawork`, `/ultrapilot` 최대 5 워커 동시 실행 |
| 검증 루프 (섹션 4) | `/ultraqa` — test → verify → fix 순환, Architect 검증 포함 |
| 모호성 제거 (섹션 6) | `/deep-interview` — 소크라테스식 질문으로 요구사항 명확화 |
| 세션 관리 / 병렬성 (이 섹션) | `/omc-teams` (tmux 기반 팀 런타임), `/project-session-manager` (Worktree 기반) |
| 관찰 가능성 (이 섹션) | HUD 상태바 + Discord/Slack/Telegram 알림 |

한 플러그인 안에 발표 4~6 섹션의 **거의 모든 개념이 명령어로 번역**되어 있다.


## OMC의 구성 — 실행 모드, 에이전트, 스킬

### 실행 모드 — "어떤 방식으로 일할 것인가"

OMC의 핵심 개념은 **실행 모드**다. 같은 작업이라도 모드에 따라 에이전트가 다르게 동작한다. 사람이 "오늘은 빠르게", "오늘은 꼼꼼하게"를 말하듯이.

| 모드 | 한 줄 요약 | 언제 |
|------|-----------|------|
| `/autopilot` | 완전 자율: 아이디어 → 작동 코드 | 엔드투엔드 기능 개발 |
| `/ultrapilot` | 최대 5 워커 병렬, 3~5배 속도 | 대규모 리팩토링 |
| `/ralph` | Architect 검증 포함 지속 루프 | 정확성이 중요한 작업 |
| `/team [count]:[model] "[task]"` | 정식 파이프라인 (plan → prd → exec → verify → fix) | 구조화된 팀 작업 |
| `/ultrawork` | 병렬 버스트 모드 | 대량 수정 |
| `/ultraqa` | test → verify → fix 순환 | QA 집중 |
| `/deep-interview` | 소크라테스식 요구사항 인터뷰 | 모호한 요구사항 |
| `/ecomode` | 비용 최적 라우팅 | 장시간 배치 작업 |

**핵심 인사이트**: 각 모드는 섹션 6의 **멀티 에이전트 패턴**을 프리셋으로 만든 것이다. `/team`은 Orchestrator 패턴, `/ultrawork`는 Parallel Agents, `/ralph`는 Ralph Loop + Verify, `/ultraqa`는 GAN-Style 검증 루프다.

### 에이전트 카탈로그 — 29개의 전문가

OMC에는 이미 29개가 넘는 전문 에이전트가 사전 정의되어 있다. 각각 다른 시스템 프롬프트, 다른 도구 권한, 다른 모델을 쓴다.

- **분석**: `architect` (Opus/Sonnet/Haiku 3단계), `analyst`, `tracer`
- **실행**: `executor` (3단계), `designer`, `writer`
- **탐색**: `explore` (Haiku, 빠름), `explore-high` (Opus, 정교)
- **검증**: `critic`, `code-reviewer`, `security-reviewer`, `qa-tester`, `test-engineer`
- **특수**: `debugger`, `scientist`, `document-specialist`, `vision`

사용자는 "이 일에 어떤 에이전트가 필요한지" 고민할 필요가 없다. OMC가 작업을 보고 알아서 고른다. 섹션 6에서 본 "서브에이전트 위임"이 **사용자 입장에서는 투명하게** 처리된다.

### 모델 라우팅 — 비용의 비밀

| 작업 특성 | 할당 모델 |
|----------|----------|
| 빠른 조회, 단순 변경, 파일 탐색 | Haiku |
| 표준 기능 구현, 리팩토링 | Sonnet |
| 복잡한 추론, 아키텍처 결정, 비평 | Opus |

이 라우팅만으로 **토큰 비용이 30~50% 줄어든다**. 사람이 매번 "이 작업은 Sonnet으로, 저 탐색은 Haiku로"를 결정할 필요가 없다.

## OMC로 보는 Agent Loop — 다섯 단계로 돌아가는 하네스

OMC가 강력한 이유는 명령어 몇 개로 **섹션 4의 Agent Loop 전체**를 돌릴 수 있기 때문이다. 이해 → 계획 → 실행 → 검증 → 학습의 다섯 단계가 각각 하나의 명령으로 매핑된다.

```
이해(Understand)  →  /deep-dive   →  암묵지 추출
계획(Plan)        →  /ralplan     →  계획 + 비평 분리
실행(Act)         →  /team        →  멀티 에이전트 병렬
검증(Verify)      →  /ultraqa     →  루프 수렴
학습(Learn)       →  /learner     →  Self-improving
```

각 명령이 무엇을 해주는지 한 번에 살펴보자. 개별 사용법 디테일은 OMC 문서에 있으니, 여기서는 **어떤 원리를 어떻게 자동화해주는가**에 집중한다.

---

### 1. `/deep-dive` — 암묵지 추출

**원리**: 섹션 4에서 말한 "**암묵지 명시화**"의 자동화 버전.

`/deep-dive`는 두 단계 파이프라인이다:
1. **Trace** — 현재 코드베이스를 먼저 훑는다 (증거 수집)
2. **Deep Interview** — 그 증거를 바탕으로 소크라테스식 질문을 연쇄

사용자가 모호한 한 문장("이런 거 하고 싶은데 정확히는 모르겠어")을 던지면, 에이전트가 질문을 던져가며 **사용자 본인도 몰랐던 엣지 케이스**를 끌어낸다. 결과물은 **구조화된 분석 — 명확한 것·모호한 것·누락된 것·가정한 것**이 분리되어 출력된다.

**핵심 가치**: 머릿속에만 있던 판단 기준이 **파일로 떨어진다**. 발표 전체 메시지인 "글쓰기가 새로운 코딩"의 가장 직관적인 구현.

---

### 2. `/ralplan` — 계획 + 비평 분리

**원리**: 섹션 4의 **Plan-Critic-Build** 루프.

일반 `/plan`과 달리, `/ralplan`은 **합의 기반 계획**이다. 흐름:
1. `architect` 에이전트가 스펙을 읽고 기술 계획 작성
2. `critic` 에이전트가 **별도 컨텍스트**에서 그 계획을 비평 — 누락·과설계·리스크·모순
3. 사용자 화면에 **계획과 비평이 나란히** 출력
4. 합의되지 않은 부분은 재논의, 승인된 부분만 실행 허가

핵심은 critic이 **architect의 작업 과정을 모른다는 것**. 최종 계획만 본다. 같은 에이전트가 자기 계획을 자기가 비평하면 blind spot이 그대로 남는다 — 섹션 6의 "검증 주체 분리" 원칙이 **계획 단계에서** 적용된 것.

**핵심 가치**: 실행 전에 한 번 잡으면 실행 이후의 수정 비용이 훨씬 싸진다. 가장 자주 쓰게 되는 명령 중 하나.

---

### 3. `/team` — 멀티 에이전트 병렬 실행

**원리**: 섹션 6의 **Parallel Agents + Orchestrator** 패턴.

`/team 4:sonnet "task"`를 실행하면 OMC가 자동으로 4개 워커를 구성한다. 워커는 각자 다른 역할(backend / frontend / test / reviewer)을 잡고 **독립된 컨텍스트**에서 병렬로 일한다. HUD 상태바에 누가 무엇을 얼마나 했는지 실시간 표시.

특히 **Test Writer 워커는 구현 코드를 보지 못한다** — 섹션 3에서 다룬 AI 치팅 방지의 자동화. 사용자가 일일이 서브에이전트를 설정하지 않아도 OMC가 역할 격리를 기본으로 깔아준다.

**핵심 가치**: 하나의 에이전트가 2시간 동안 돌지 않고, **5분짜리 워커 여럿이 병렬로** 돌아 같은 시간에 더 많이 끝낸다 — 섹션 6의 "5분 에이전트 × N" 철학의 실전 구현.

---

### 4. `/ultraqa` — 검증 루프 수렴

**원리**: 섹션 4의 **Agent Loop**에서 "Verify가 심장"이라는 명제.

`/ultraqa`는 테스트·검증·수정을 자동으로 순환한다:
```
테스트 실행 → 실패 수집 → debugger가 원인 분석 → executor가 수정 → 재실행 → ...
```

통과할 때까지 (또는 N회 제한) 반복된다. Verify 에이전트는 **별도 컨텍스트**에서 검증하므로 "자기 코드를 자기가 리뷰"하는 일이 없다.

**핵심 가치**: 사람이 터미널 앞에 앉아 있지 않아도 **루프가 알아서 수렴**한다. 슬랙 알림 받고 돌아오면 통과된 상태. 이것이 섹션 4의 "검증이 심장"이라는 말의 실제 모습.

---

### 5. `/learner` — Self-Improving Harness

**원리**: 섹션 4의 **Self-Improving Harness** — 시스템이 쓸수록 자란다.

세션이 끝날 무렵 `/learner`를 실행하면 OMC가 방금 세션에서 **재사용 가능한 패턴을 추출**한다. "이 작업은 반복될 가치가 있다"고 판단되는 흐름을 **새 스킬 파일로 자동 저장**. 사용자가 수동으로 CLAUDE.md에 "이거 다음에도 쓰고 싶어"를 적을 필요가 없다.

**핵심 가치**: 쓸수록 스마트해지는 시스템. 이번 세션에서 배운 것이 **다음 세션의 기본값**이 된다. 발표 전체의 메시지 "암묵지가 시스템으로 승격된다"의 실제 구현.

---

### 다섯 단계가 묶어서 보여주는 것

```
1. /deep-dive   —  내 머릿속이 파일로 떨어진다       (암묵지 명시화)
2. /ralplan     —  계획과 비평이 분리되어 있다       (Plan-Critic-Build)
3. /team        —  에이전트가 팀으로 돈다            (멀티 에이전트)
4. /ultraqa     —  루프가 알아서 수렴한다            (Agent Loop · Verify)
5. /learner     —  시스템이 자신을 확장한다          (Self-Improving)
```

사용자가 치는 명령은 다섯 개. 그 뒤에서 돌아가는 것은 **발표 4~6 섹션에서 다룬 원리 전체**다. 이것이 "원리를 이해한 사람이 좋은 플러그인을 쓸 때" 일어나는 일이다.

그리고 다시 확인 — **사용자가 이 원리들을 모르면**, 명령어 다섯 개만 외워 쓰는 것으로는 같은 효과가 나지 않는다. 결과가 이상할 때 왜 이상한지 판단할 수 없기 때문이다. **원리가 먼저, 명령어는 그 다음**이다.

## 한 걸음 더 — Claude 하나에 의존하지 않는다

지금까지는 "여러 Claude 에이전트가 역할을 나눠 일한다"는 관점이었다. 여기서 한 걸음 더 나갈 수 있다 — **서로 다른 AI 모델(Claude, Codex, Gemini 등)을 함께 쓰는 것**이다. 섹션 6의 멀티 에이전트가 "여러 Claude"였다면, 이건 "여러 **종류의 AI**"다.

### 왜 한 모델에 의존하지 않는가

모델마다 강점이 다르다. 일반화하면:
- 하나의 모델은 **특정 유형의 추론·코드·컨텍스트**에서 더 강하다
- 같은 질문이라도 **다른 훈련 분포**에서 나온 답은 서로 다른 blind spot을 가진다
- **비용 구조**도 다르다 — 어떤 작업은 한 모델이, 다른 작업은 다른 모델이 훨씬 저렴

한 모델에 의존하면 그 모델의 편향을 그대로 받는다. 여러 모델을 **병렬로 조회하고 교차 검증**하면, 각자의 blind spot을 서로 상쇄한다. Karpathy가 "LLM Council"이라고 부른 개념이 이것이다 — 중요한 결정을 여러 모델에게 동시에 묻고 합의를 도출한다.

### OMC의 두 가지 지원

OMC는 이 "다중 모델 협업"을 두 가지 명령으로 제공한다:

**`/ask [provider] "[prompt]"`** — 특정 공급자에게 바로 질의
```
/ask codex "이 함수의 성능 개선 방법"
/ask gemini "이 알고리즘의 시간 복잡도 분석"
```
같은 세션 안에서 필요에 따라 **공급자를 골라** 묻는다. Claude의 답이 확신이 안 설 때 다른 모델에게 의견을 구하는 식.

**`/ccg`** — Claude-Codex-Gemini 트리 오케스트레이션
세 모델에게 **동시에** 질문을 던지고, 답을 모아서 비교한다. 구조는 간단하다:
1. 질문을 세 모델에 병렬 송출
2. 각 모델의 답 수집
3. **합의된 부분**과 **엇갈리는 부분**을 명확히 분리
4. 사용자가 엇갈리는 부분만 보고 판단

사용자는 세 모델의 답을 **일일이 복붙할 필요가 없다**. 하나의 명령어로 "세 개의 뇌"를 동시에 쓴다.

### 이 패턴이 특히 빛나는 순간

- **아키텍처 결정** — 되돌리기 어려운 큰 결정일수록 여러 관점이 필요
- **디버깅이 막힐 때** — 한 모델이 같은 길만 반복할 때, 다른 모델이 완전히 다른 가설을 제시
- **외부 문서 조회/리서치** — 훈련 데이터가 다른 모델들은 서로 다른 것을 알고 있다
- **코드 리뷰 최종 확인** — 여러 모델이 동시에 통과시켜야 자신 있게 머지
- **비용 최적화** — 드래프트는 저렴한 모델, 비평·검증은 강한 모델

### 그냥 "여러 모델 쓰기"와 무엇이 다른가

사람이 수동으로 여러 CLI를 번갈아 쓰는 건 이미 많은 사람들이 한다. 핵심 차이는 **자동 조율**이다:
- 세 모델의 답이 **구조화된 한 화면**에 모임
- **합의·불일치·불확실**이 분리되어 보임
- 사용자는 "다른 답을 하는 부분"에만 집중하면 됨
- 여러 CLI를 띄우고 복붙하는 **인지 비용이 거의 0**

이것이 섹션 6의 **"조율되지 않은 병렬"과 "조율된 병렬"의 차이**를 모델 단위에서 구현한 것이다.

### 주의점

- **가격이 쌓인다** — 세 모델에 같은 질문을 던지면 비용도 세 배. 중요한 결정에만 쓴다
- **속도가 느려질 수 있다** — 가장 느린 모델에 맞춰 응답이 돌아온다
- **합의가 항상 정답은 아니다** — 세 모델이 같은 훈련 분포의 편향을 공유할 수도 있다. 합의는 **신호**지 **증명**이 아님
- **구독/API 키 필요** — Codex, Gemini는 각각 별도 인증. OMC가 라우팅은 해주지만 계정은 사용자가 준비

### 섹션 6과의 구분

용어를 정리해두자:
- **멀티 에이전트** (섹션 6) — 여러 Claude 인스턴스가 **다른 역할**로 협업
- **멀티 모델** (이 섹션) — 여러 **종류의 AI**가 **같은 질문**에 답하고 교차 검증

두 개는 겹치지 않고 **같이 쓸 수 있다**. 예: `/team` 안에서 각 워커가 다시 `/ccg`로 중요한 결정을 세 모델에 물어보는 식. 하네스가 깊어질수록 청중은 "와 이렇게까지 쓸 수도 있구나"를 느낀다.

## OMC가 해결하지 못하는 것 — 주의점

OMC가 마법은 아니다. 섹션 5(한계와 실패 패턴)는 여전히 유효하다.

### 1. 원리를 모르면 블랙박스가 된다
`/team`을 실행했는데 결과가 이상할 때, **왜 이상한지**를 판단하려면 섹션 4~6의 원리를 이해해야 한다. 모르면 "AI가 또 이상하게 했네"로 끝난다. OMC는 원리 이해를 **대체하지 않고 가속**한다.

### 2. 컨텍스트 실패 모드는 여전하다
섹션 4의 Context Poisoning/Distraction/Confusion/Clash는 플러그인 레이어에서도 발동한다. OMC가 관리하지만 완벽하지 않다. 긴 세션은 여전히 주기적으로 끊고 다시 시작해야 한다.

### 3. 이슈 트래커/코드베이스에 대한 지식은 사용자가 넣어야 한다
OMC는 프로젝트 고유 지식을 모른다. CLAUDE.md·팀 규칙·이슈 트래커 연동·MCP 설정은 **여전히 사용자가 직접 세팅**해야 한다. OMC는 "오케스트레이션의 일반 원리"를 제공하지, "이 프로젝트의 맥락"을 제공하지는 않는다.

### 4. 플러그인 의존의 리스크
플러그인이 업데이트되면 동작이 바뀐다. 깨지기도 한다. **중요한 워크플로우일수록 "플러그인이 없어도 동작하는 최소 경로"를 알고 있어야** 한다. OMC를 쓰지 않아도 서브에이전트·Plan Mode·Worktree는 그대로 쓸 수 있다.

### 5. 비용
병렬 5워커 × Opus 라우팅은 싸지 않다. OMC의 `/ecomode`나 모델 라우팅으로 30~50% 절감된다지만, **무지막지하게 쓰면 여전히 비싸다**. 토큰 모니터링을 켜둔다.

## 네 가지 축을 OMC가 어떻게 커버하는가 (요약)

발표 초반에 언급한 네 축을 OMC에 매핑해보면 이렇다. 이것이 "한 플러그인이 어떻게 이만큼을 커버하는가"의 답이다.

| 축 | 원리 (섹션 4·6) | OMC 구현 |
|----|----------------|---------|
| **작업 단위 관리** | Plan Mode + 이슈 앵커링 | `/deep-interview` + `/ralplan` |
| **병렬성** | Worktree + 멀티 세션 + Parallel Agents | `/project-session-manager` + `/team` + `/ultrawork` |
| **컨텍스트 이어가기** | CLAUDE.md + 핸드오프 + 메모리 | `/omc-setup` 기본 CLAUDE.md + `/learner`로 스킬 추출 |
| **반복 패턴 자동화** | Command + Skill + Hook | 31개 이상의 사전 정의 스킬 + 훅 자동 설정 |

**없는 것은 딱 하나** — 이 프로젝트의 맥락. 그건 여전히 사용자가 CLAUDE.md에 써넣어야 한다.

## 일상 패턴 네 가지 — OMC에서는 이렇게

섹션 초반 버전에서 다뤘던 **코드 리뷰 / 디버깅 / PR 생성 / 테스트**를 OMC에서는 어떻게 하는지 짧게.

| 일상 작업 | OMC 사용법 | 뒤에서 일어나는 일 |
|----------|-----------|------------------|
| 코드 리뷰 | `security-reviewer`, `code-reviewer` 에이전트 명시 호출 | 섹션 6의 검증 주체 분리 |
| 디버깅 | `/trace` 또는 `/deep-dive` (trace → deep-interview 파이프라인) | 증거 기반 원인 추적 |
| PR 생성 | `/team` 워크플로우의 마지막 단계로 자동 | diff + 스펙 → PR 본문 템플릿 |
| 테스트 작성 | `/ultraqa` 또는 `test-engineer` 호출 | TDD 사이클 강제, 치팅 방지 |

이전 버전의 이 섹션에 있던 "TDD, 검증 주체 분리, 구조화된 리뷰 출력 포맷" 같은 원칙은 **OMC 안에 이미 들어있다**. 사용자는 명령어만 쓰면 된다.

## 플러그인을 고를 때의 체크리스트

OMC 외에도 좋은 플러그인은 많다. 무엇을 고를지는 본인 프로젝트의 병목에 달려 있다. 고를 때 보는 5가지:

1. **원리가 보이는가** — 플러그인 문서를 읽고 "어떤 원리를 구현한 것인지" 설명할 수 있는가. 못 하면 블랙박스 의존
2. **깰 수 있는가** — 플러그인 없이도 같은 작업이 (느리더라도) 가능한가. 종속성이 과하면 위험
3. **관찰 가능한가** — 뒤에서 무엇을 하는지 로그·HUD·알림으로 볼 수 있는가
4. **유지되는가** — 마지막 커밋이 몇 달 전인지. 생태계는 빨리 움직인다
5. **내 병목에 맞는가** — "멋있어 보이는 것"이 아니라 **내가 실제로 자주 하는 작업에 시간을 줄이는가**

---

## 자주 하는 실수

1. **플러그인만 쓰고 원리는 모른다** — 블랙박스 의존. 이상 동작 시 디버깅 불가
2. **플러그인을 5~6개씩 동시 설치** — 서로 충돌하고 훅이 겹치며 HUD가 난장판. OMC 하나처럼 큰 것을 쓰는 중이면 보조 플러그인은 최소
3. **OMC를 쓰면서 CLAUDE.md는 비워둔다** — 프로젝트 맥락은 여전히 사용자 책임. 비어 있으면 OMC도 무용
4. **모든 작업에 `/team`** — 간단한 작업은 단일 세션이 빠르다. 팀 모드의 조율 비용을 기억한다 (섹션 6)
5. **알림을 꺼둔다** — 그러면 자리를 비울 수 없다. 알림은 "비동기 작업"의 필수 조건이다

---

## 발표용 한 장 요약

> **"원리를 이해한 사람만이 좋은 플러그인을 제대로 쓸 수 있다."**
>
> - 섹션 4~6에서 배운 원리를 매일 손으로 세팅하는 건 불가능하다
> - 다행히 커뮤니티가 대부분을 플러그인으로 패키징해뒀다
> - OMC는 그중 대표 — 한 플러그인 안에 멀티 에이전트·병렬·검증·모델 라우팅·관찰 가능성까지
> - **하지만**: 원리 이해, 프로젝트 맥락(CLAUDE.md), 최소 경로 지식은 여전히 사용자 책임
>
> "플러그인은 원리의 **가속기**이지, **대체재**가 아니다."
