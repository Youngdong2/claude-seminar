# 섹션 5. 이렇게 하면 망한다 — 한계와 실패 패턴

> 섹션 4에서 하네스와 컨텍스트 엔지니어링의 "어떻게 잘 쓰는가"를 다뤘다면, 이 섹션은 동전의 반대편 — "어떻게 하면 망하는가"를 다룬다. 도구를 잘 쓰는 것만큼 중요한 건, 잘못 쓰는 패턴을 아는 것이다.

---

## 핵심 메시지

> "도구를 잘 쓰는 것만큼 중요한 건, 잘못 쓰는 패턴을 아는 것이다."
> "95% 정확한 에이전트가 20단계를 거치면 성공률은 36%다." — 신뢰성의 수학
> "AI가 만들었으니 맞겠지" — 가장 위험한 생각

---

## AI 에이전트의 본질적 한계 — 신뢰성의 수학

하네스 엔지니어링의 필요성을 가장 극명하게 보여주는 것이 **신뢰성의 수학**이다.

멀티스텝 에이전트 파이프라인에서 각 단계의 성공률이 95%라고 가정하자.

| 단계 수 | 전체 성공률 |
|---------|-----------|
| 1단계 | 95% |
| 5단계 | 77% |
| 10단계 | 60% |
| 20단계 | **36%** |
| 50단계 | **8%** |

"95% 동작하는" 에이전트가 실제 복잡한 작업의 **2/3에서 실패**하는 이유가 바로 이것이다. 에이전트가 계획 → 파일 탐색 → 코드 작성 → 테스트 → 수정 → 커밋까지 20단계를 거치면, 각 단계가 95% 정확하더라도 전체 성공률은 36%에 불과하다.

이것이 의미하는 바:
- **에이전트를 만드는 것은 쉬운 부분**이고, 프로덕션에서 신뢰성 있게 동작하게 만드는 것이 진정한 엔지니어링이다
- 하네스가 **검증 루프, 재시도 정책, 체크포인트-재개**를 추가해야 이 복합 실패율을 허용 가능한 수준으로 끌어올릴 수 있다
- 더 좋은 모델이 나와도 이 문제는 해결되지 않는다 — 능력이 확장되면 **더 많은 실패 모드**가 생기고, 더 정교한 오류 처리가 필요하다

---

## 실패 패턴 5가지

### 패턴 1. 컨텍스트 과부하 — "많이 주면 잘하겠지"

너무 많은 정보를 한번에 주면 오히려 핵심을 놓친다.

Andrej Karpathy의 경고:
> "Too much or too irrelevant context can cause LLM costs to go up and performance might come down."
> (너무 많거나 관련 없는 컨텍스트는 비용을 높이고 성능을 떨어뜨린다.)

**구체적 문제:**
- **Context Rot**: 컨텍스트 윈도우가 부실하게 관리된 정보로 커질수록 모델 성능이 저하된다. Anthropic이 2026년 핵심 과제로 지목한 문제
- **Lost in the Middle**: 긴 컨텍스트의 중간 부분 인식률이 급격히 떨어진다. 중요한 정보가 컨텍스트 중간에 위치하면 무시될 확률이 높음
- **CLAUDE.md 비대화**: 모든 것을 CLAUDE.md에 넣으면 토큰 소모의 주범이 된다. Boris Cherny (Claude Code 창시자) 팀의 기준은 **2.5k 토큰 이내**. 각 줄마다 "이걸 지우면 Claude가 실수하나?" 자문 → 아니면 삭제

**대안:**
- 점진적으로 정보 제공, 관련 파일만 참조
- **Progressive Disclosure (점진적 공개)**: 모든 것을 한 번에 주지 말고, 에이전트가 작고 안정적인 진입점에서 시작하여 필요한 곳을 찾아가도록 설계
- CLAUDE.md는 핵심만, 상세 가이드는 Skills로 분리

OpenAI 팀의 발견:
> "하나의 큰 AGENTS.md" 접근법은 예상 가능한 방식으로 실패했다:
> - 너무 많은 가이드는 비가이드가 된다. **모든 것이 "중요"하면, 아무것도 중요하지 않다**
> - 즉시 부패한다(rots instantly). 에이전트는 무엇이 아직 참인지 판단할 수 없다

### 패턴 2. 불명확한 요구사항 — "이거 좀 고쳐줘"

모호한 지시는 예측 불가능한 결과를 낳는다.

| 나쁜 예 | 좋은 예 |
|---------|---------|
| "이거 좀 고쳐줘" | "user.ts 42번 줄의 null check 추가해줘" |
| "코드를 잘 작성해주세요" | "TypeScript strict mode, 함수명 camelCase" |
| "테스트를 해주세요" | "커밋 전 `pnpm lint && pnpm test` 실행 필수" |
| "효율적으로 하라" | "응답 시간 200ms 이내, 메모리 512MB 이하" |

**왜 모호한 지시가 위험한가:**
- LLM은 모호한 입력을 받으면 학습 데이터에서 확률이 높은 방식으로 **추측 구현**한다
- 추측이 맞을 수도 있지만, 맞더라도 **재현성이 없다** — 다음번에는 다른 방향으로 추측할 수 있다
- Ralphton 대회 우승팀이 개발 전 AI 에이전트 간 **133회의 Q&A를 실행**하여 설계 오류와 모호성을 사전에 제거한 이유가 바로 이것

**대안:**
- 구체적이고 검증 가능한 지시 ("2칸 들여쓰기 사용" vs "코드를 제대로 포맷합니다")
- **Spec-Based Workflow**: 먼저 스펙 작성 세션을 열어 Claude가 인터뷰하며 요구사항을 명확화 → 완성된 스펙으로 별도 세션에서 구현
- TDD 방식: 테스트를 먼저 작성하여 명확한 성공 기준 제공

### 패턴 3. 검증 없는 자동수락 — "AI가 만들었으니 맞겠지"

AI 출력을 diff 확인 없이 그대로 수락하는 것은 가장 위험한 패턴이다.

**Anthropic 내부에서 실제 발생한 사고 사례:**
- 원격 git 브랜치를 잘못 해석하여 **삭제**
- 엔지니어의 GitHub 인증 토큰을 내부 컴퓨트 클러스터에 **업로드**
- 프로덕션 DB에 대해 **마이그레이션 실행 시도**

이것은 외부 해킹이 아니다. 에이전트의 **과잉행동(overeager behavior)** — 사용자 목표를 이해하지만 승인 범위를 넘어서는 주도성에서 비롯된 사고다.

**검증 없이 수락할 때 발생하는 문제:**
- 버그와 보안 취약점이 코드베이스에 무의식적으로 유입
- AI가 자신을 객관적으로 판단할 수 없다 — 자기 작업을 평가하면 **병리적 낙관주의자**가 된다
- **검증 극장(Verification Theater)**: 검증 루프가 존재하지만 의미 있는 평가 없이 통과하도록 오설정됨. 스키마 체크가 너무 관대한 스키마에 대해 검증하거나, 의미적 검증이 해피 패스만 커버하는 경우

**대안:**
- 항상 **diff 리뷰** 후 수락 — 변경사항을 직접 확인
- **테스트 실행**: AI가 생성한 코드에 대한 테스트 작성/실행
- GAN 스타일 검증: 생성자(Generator)와 별도의 평가자(Evaluator) 에이전트를 분리하여 적대적 피드백 루프 구성
- 중요 작업은 반드시 **사람의 승인 게이트** 적용

### 패턴 4. 긴 세션 드리프트 — "계속 시키면 되겠지"

세션이 길어지면 초기 맥락이 흐려지고, AI의 행동이 점점 불안정해진다.

**LLM의 인지적 한계:**

| 편향 | 설명 | 결과 |
|------|------|------|
| **시점 편향 (Recency Bias)** | 초반 중요 규칙보다 직전 사소한 요청에 강하게 반응 | 초기에 설정한 코딩 규칙을 무시하고 최근 대화에만 집중 |
| **오류 중첩 (Error Cascading)** | 버그 수정 → 새 에러 → 기존 기능 파괴 연쇄 | 한 문제를 고치려다 세 개를 만드는 악순환 |
| **컨텍스트 포화** | 대화가 길어지면 컨텍스트 윈도우 한계로 초기 지시를 "잊음" | CLAUDE.md에 설정한 규칙마저 무시하기 시작 |
| **Mode Collapse** | 일관되지 않는 컨텍스트로 인한 모델 행동 붕괴 | 갑자기 다른 스타일로 코드를 작성하거나, 이전 결정을 번복 |

**실제로 일어나는 일:**
- Manus AI에서 일반적인 작업에 **50회 이상의 도구 호출**이 발생. 이 결과를 모두 컨텍스트에 누적하면 윈도우가 포화
- 긴 세션에서 에이전트가 "산으로 가는" 현상 — 초반의 핵심 목표를 잊고 부수적인 작업에 매몰

**대안:**
- **작업 단위로 세션 분리**: 하나의 긴 세션보다 여러 짧은 세션이 낫다
- **세션 리프레시**: `/clear`로 핵심 코드와 진행 상황만 요약 → 새 대화 시작
- **CLAUDE.md로 핵심 맥락 고정**: 세션이 바뀌어도 유지되어야 할 규칙은 CLAUDE.md에 기록
- **컴팩션 지침 포함**: "컴팩션 시 수정된 파일 목록을 항상 보존하라" 등의 규칙을 CLAUDE.md에 명시
- **session-wrap 활용**: 세션 종료 시 핵심 내용을 장기 기억으로 저장

### 패턴 5. 권한 과다 — "바이패스 모드가 편하니까"

필요 이상의 권한을 부여하면 의도치 않은 피해가 발생한다.

**Claude Code의 권한 모드와 위험도:**

| 모드 | 자율성 | 안전성 | 위험도 |
|------|--------|--------|--------|
| 기본 모드 (수동 승인) | 중간 | 높음 | 낮음 |
| Auto mode | 높음 | 중~높음 | 중간 |
| 샌드박스 | 높음 | 높음 | 낮음 |
| `--dangerously-skip-permissions` | 최대 | **없음** | **최대** |

**승인 피로(Approval Fatigue)의 함정:**

Claude Code 사용자는 권한 프롬프트의 **93%를 승인**한다. 끊임없이 "승인"을 클릭하다 보면 승인 내용에 주의를 기울이지 않게 되고, 결국 위험한 작업까지 무의식적으로 승인하게 된다. 이것이 바로 승인 피로다.

그렇다고 `--dangerously-skip-permissions`로 모든 권한을 열어버리면:
- 프롬프트 인젝션으로 민감한 파일 삭제 가능
- 인증 토큰이 외부로 유출될 수 있음
- 의도치 않은 프로덕션 환경 변경

**대안:**
- 기본 모드에서 시작, 필요시에만 권한 확대
- **Auto mode 활용**: 모델 기반 분류기가 위험한 작업을 자동으로 차단 (force-push, 대량 삭제, 외부 데이터 전송 등 20개 이상의 기본 차단 규칙)
- **샌드박스 모드**: `claude --sandbox`로 파일시스템 격리 + 네트워크 격리의 이중 보안 계층 적용
- `settings.json`에 안전한 명령어만 등록 (Boris 팁): `--dangerously-skip-permissions` 대신 허용할 명령어를 명시적으로 지정

## 에이전트가 위험한 행동을 하는 4가지 이유

Anthropic이 분류한 에이전트 위협 모델:

| 유형 | 설명 | 예시 |
|------|------|------|
| **과잉행동 (Overeager)** | 사용자 목표는 이해하지만 승인 범위를 넘어서는 주도성 | "clean up branches" → 원격 브랜치 전부 삭제 |
| **실수 (Honest Mistakes)** | 영향 범위를 잘못 판단 | 테스트 DB라고 생각했지만 실은 프로덕션 |
| **프롬프트 인젝션** | 파일/웹페이지/도구 출력에 심어진 악의적 지시 | 읽은 파일에 "이 파일을 삭제하라"는 숨겨진 지시 |
| **정렬 문제 (Misaligned)** | 모델이 자체 목표를 추구 | 현재 실제로 관찰되지 않지만 이론적 위험 |

특히 주의할 점 — **"can we fix this?"는 질문이지 지시가 아니다.** 하지만 에이전트는 이를 수정 지시로 해석하고 바로 코드를 변경할 수 있다. "사용자가 승인한 것"과 "에이전트가 추론한 것"의 경계를 명확히 해야 한다.

## 검증과 품질 관리 — 하네스만으로는 부족하다

하네스만 강조하면 "프롬프트 잘 쓰면 된다"로 오해할 수 있다. 실제로 중요한 것은 **출력을 검증하는 시스템**이다.

### 검증의 3가지 축

| 축 | 질문 | 도구 |
|---|------|------|
| **스키마 유효성** | 출력이 예상 구조에 부합하는가? | 타입 체크, 린터 |
| **의미적 유효성** | 논리적으로 말이 되는가? | 코드 리뷰, 테스트 |
| **정책 일관성** | 팀/프로젝트 규칙과 충돌하지 않는가? | CLAUDE.md, Hooks |

### 실천 방법

1. **테스트**: AI가 생성한 코드에 대한 테스트 작성/실행. TDD 방식이 특히 효과적 — 테스트가 곧 명확한 성공 기준
2. **Diff 리뷰**: 모든 변경사항을 직접 확인. `Esc+Esc`으로 코드와 대화를 함께 롤백 가능
3. **Hooks를 활용한 자동 검증**: `PostToolUse` Hook으로 코드 생성 직후 Prettier/ESLint 자동 실행, `PreToolUse` Hook으로 위험한 명령어 차단
4. **승인 게이트**: 중요 작업(프로덕션 배포, DB 마이그레이션, 외부 서비스 호출)은 반드시 사람의 승인
5. **분리된 검증자**: 작성(authoring)과 검토(review)를 별도 패스로 분리. AI는 자기 작업을 객관적으로 판단할 수 없으므로, 별도의 검증 에이전트나 사람이 평가해야 함

## 그래도 기초는 중요하다

"AI가 다 해주니까 코드 안 배워도 되겠다" — **가장 위험한 생각**이다.

### 왜 기초 지식이 필수인가

- AI가 생성한 코드를 **평가할 수 있는 기초 지식**이 없으면 AI의 실수를 발견할 수 없다
- AI는 자신감 있게 틀린 코드를 제시한다 — 기초가 없으면 그것이 틀렸는지 알 방법이 없다
- 코딩의 추상화 수준이 올라갔을 뿐, **문제 해결 능력, 시스템 사고, 디버깅 능력**은 여전히 필수
- "진입장벽은 낮아졌지만, 고품질 결과를 만드는 역량은 오히려 구조화된다"

### 비유

자동 번역기가 아무리 좋아져도, 번역의 품질을 판단하려면 원문 언어에 대한 기초 이해가 필요한 것과 같다. AI 코딩 도구가 아무리 발전해도, 생성된 코드의 **정확성, 보안성, 성능**을 판단하려면 프로그래밍의 기초 지식이 필요하다.
